# ShelfRow (Stackroom Remake) 設計仕様書 (Design & Architecture Document)

本ドキュメントは、レガシーmacOSアプリケーション「Stackroom」のコンセプトと資産（ライブラリデータ、表紙サムネイル）を現代のmacOS（SwiftUI / SwiftData）環境に継承・近代化し、セキュアかつ高速に動作させるための設計仕様である。

他開発者（人間およびAI）が、本システムの設計背景、意図、モデリング、およびデータ構造をMECE（相互に排他的で、全体として漏れがない）に理解し、実装・保守できることを目的とする。

> 運用ルール: 仕様・挙動・データ構造・重要な不具合修正が変わった場合は、コード修正と同じタイミングで本書と `documents/update_history.md` を更新する。

---

## 1. 背景と課題 (Background & Context)

### 1.1 背景
「Stackroom」は、2004年頃にリリースされた、自炊（スキャン）したコミック、同人誌、画像フォルダ、ZIPアーカイブをiTunesライクに整理・管理・閲覧できるmacOSアプリケーションである。
長年にわたりメンテナンスが停止しているが、その操作性の高さと優れた蔵書管理機能から、膨大な蔵書資産を抱えるユーザーにとって代替困難な存在となっている。

### 1.2 解決すべき課題
1. **インフラの近代化:** 
   旧アプリはローカルメモリ上ですべてを処理し巨大なXMLファイル（実際はPLIST形式）で永続化していた。書籍数が2万件近くなると起動時間や保存時のI/O負荷が限界に達するため、堅牢なリレーショナル・データベース（RDB）による遅延ロードが不可欠。
2. **サンドボックスとセキュリティ制約への適応:** 
   現代のmacOSのセキュリティモデル（Sandbox）下では、アプリ外部のストレージ（外付けHDD、NAS等）にある書籍ファイルへのアクセス権限を安全に永続保持（Security-Scoped Bookmark）する必要がある。
3. **パス一括付け替え問題:** 
   外付けドライブの買い替えやマウントポイントの変更によって書籍データの絶対パスが変わった際、数万件のアイテム情報を個別に書き換えることなく、一括でアクセス権とパスをマッピングできる構造が必要。
4. **レガシー資産（サムネイル画像）の完全インポートと自立化:** 
   旧アプリが生成した約2万件の表紙サムネイル画像（`thumbnail.jpg`）を、一度のXMLインポート処理で完全に新アプリ側のローカルストレージへコピー移行し、インポート完了後に旧アプリフォルダを安全に完全削除できる仕組みが必要。

## 2. システム要件・仕様 (Requirements & Specifications)

### 2.1 機能要件 (Functional Requirements)
*   **レガシーXMLインポート:** 旧アプリの `Stackroom Library.xml` を非同期でパースし、書籍・フォルダ階層・スマートフォルダ定義を完全移行。
*   **制御文字の自動クレンジング:** 旧アプリのバグや古いPLIST保存APIが書き出した、XML 1.0仕様違反の不正な制御コード（`\x01`〜`\x08`等）を事前検知・自動除去。
*   **一括サムネイル移民（マイグレーション）:** インポート時に、旧アセットフォルダ（`Stackroom Library/[ID]/thumbnail.jpg`）から新アプリのプライベートキャッシュ領域へサムネイル画像を物理的に丸ごとコピー。
*   **ボリュームベース相対パス管理:** 書籍ファイルを「親ボリューム（絶対マウントパス＋権限）」と「相対パス」に分離して保持し、ボリューム移行時は「親ボリューム」のみを再選択して再解決する。
*   **3ペイン macOS ネイティブ UI:** ミュージックアプリ（旧iTunes）に倣ったサイドバー、メインコンテンツ（グリッド/リスト）、編集インスペクタを搭載。サイドバーは蔵書管理の主軸なので常時表示し、格納操作は提供しない。左右ペインはユーザー調整幅を維持・記憶し、ウィンドウサイズ変更時の増減は中央のリスト/グリッド領域で吸収する。
*   **外部ビューア連携 & Finder表示:** お気に入りの外部コミックビューア（EdgeView等）でのファイル起動、およびFinder上での選択ファイル表示。
*   **D&D登録先:** ファイル/フォルダをメイン画面へドラッグ&ドロップした場合、常にライブラリへ登録する。通常シェルフを表示中なら、そのシェルフにも同時に追加する。スマートシェルフ表示中は条件一致で自動表示されるため、手動所属は変更しない。
*   **ファイル名フォーマット解析:** 環境設定 > カスタマイズの「フォーマットのカスタマイズ」で、D&D登録およびタイトル補完時のファイル名解析書式を指定できる。対応プレースホルダは `@author`（作者）, `@title`（タイトル）, `@keywordA`, `@keywordB`, `@relation`（関連）, `@genre`（ジャンル）, `@type`（種類）。`[]`, `()`, `{}`, ハイフン、ホワイトスペース等の区切りは書式中のリテラルとして扱い、軽量な正規表現に変換して解析する。例えば `[@author(@keywordA)] @title` に対して `[ほげふが(太郎)] 書籍名ですよ(1).zip` は、作者=`ほげふが`、キーワードA=`太郎`、タイトル=`書籍名ですよ(1)` になる。同じ書式で `[ほげふが]書籍名ですよ(1).zip` のように一部プレースホルダが省略された場合は、作者=`ほげふが`、キーワードA=空、タイトル=`書籍名ですよ(1)` として扱う。書式に定義されていない括弧は項目境界としては扱わず、該当プレースホルダの値の一部として保持または無視される。書式に一致しない場合は従来の `(ジャンル)[作者]タイトル` 解析へフォールバックする。
*   **ヘルパー設定とD&D受け入れ:** 環境設定 > ヘルパーでは、拡張子ごとに起動アプリケーションを設定する。拡張子は1行にカンマ区切りで複数登録でき、登録済み拡張子のファイルはD&D登録でも受け入れる。ダブルクリック時は拡張子ヘルパーを優先して起動するが、これは書籍の「種類」とは独立した実行ルーティングであり、種類とヘルパーは必ずしも一致しない。
*   **新規登録時の種類自動判定:** D&D新規登録では、ファイル名フォーマットの `@type` が現在の種類名に一致した場合はその指定を最優先する。`@type` が無い場合はZIP/画像フォルダ内の画像ページ数を軽量に数え、21ページ以上=「厚い本」、11〜20ページ=「薄い本」、1〜10ページ=「本の一部」に自動分類する。`rar` / `zip` / `7z` はアーカイブ系として同じ分類ルールの対象にし、それ以外のヘルパー登録拡張子は「ムービー」として登録する。「画像セット」「テキスト」は自動判定では設定しない。0ページは明示ルール外として自動分類せず、必須フィールドの既定値である「厚い本」に留める。
*   **環境設定画面の可読性:** 設定ウインドウはmacOS Settings風のサイドバー式ナビゲーションとし、左に「一般 / ビューア / ヘルパー / キーワード / カスタマイズ / セキュリティ / 保守」、右に詳細ペインを表示する。本文サイズは13pt以上、説明文は利用可能な横幅で自然に折り返す。ヘルパー/カスタマイズ/保守などは固定小幅の入力欄を避け、全幅または2カラムの伸縮レイアウトで構成する。
*   **バックアップ設定:** 環境設定 > 保守にバックアップ設定を置く。チェックボックスで有効化し、ユーザーが選択したバックアップ先フォルダを security-scoped bookmark として保存する。「今すぐバックアップ」は対象フォルダ内の `ShelfRowBackup` に、SwiftDataのDBを含むApplication Support、ShelfRowのサムネイルキャッシュ、UserDefaults plistをコピーする。差分判定は `manifest.json` に保存した相対パス・サイズ・更新日時を使い、前回と同一のファイルはコピーしない。前回存在して今回存在しないファイルはバックアップ側から削除し、バックアップを現在のアプリデータに追従させる。「バックアップからリストア」は同じ `manifest.json` を正とし、バックアップ時点のファイルを現在の保存先へ上書き復元する。バックアップに存在しない対象ファイルは現在側から削除し、古いバックアップへの先祖返りも許容する。DB復元後の読み直しのため、完了後はアプリ再起動を促す。
*   **キーワード同一視:** 環境設定 > キーワードで、作者・ジャンル・関連・キーワードA・キーワードB・メモごとに同一視する語をグループ登録できる。例えば「作者」に `Lorem ipsum, Dolor sit, Amet` を登録すると、検索欄にグループ内のいずれかの語を入力した場合、同じグループの全語を同一フィールドに対して検索候補へ展開する。設定は `keywordEquivalenceRulesJson` にJSON保存し、検索時だけ軽量に評価する。キーワードチップから設定画面を開く場合は、SwiftUI の Settings シーンを `openSettings` で開き、事前に選択種類とキーワードを `UserDefaults` 経由で渡す。設定行は削除時の配列範囲外参照を避けるため、`ForEach($rules)` ではなく安定IDから都度 Binding を作る。誤操作防止のため一括削除ボタンは設けず、削除は各行単位で行う。
*   **カスタマイズ画面の入力欄:** ダークテーマで背景と同化しないよう、フォーマット欄・種類名・項目名のテキストボックスは明示的な入力背景、細い境界線、最小限の影を持つ。フォーマット欄は記号とプレースホルダを読み取りやすくするため等幅表示にする。

### 2.2 非機能要件 (Non-Functional Requirements)
*   **応答性 (Responsive UI):** メインスレッド（UI描画）を絶対にブロックしない。2万件のインポート、サムネイル生成、パスの書き換え、ビューアの起動、すべてを Swift Concurrency (`Task` / `actor`) で非同期化。
*   **軽量性 (Lightweight Implementation):** ShelfRow の特徴は「軽量に大量蔵書を扱えること」。選択操作でフィルタ/ソートを再計算しない、ZIP一覧を再解析しない、存在しないサムネイルを画像デコーダに渡さない、全件通知で全カバーを再ロードしない、などの方針を仕様として扱う。
*   **メモリ効率 (Memory Efficiency):** 2万件の画像を一度にRAMへロードしない。`NSCache` による画面外画像の自動パージと、`CGImageSource` の縮小サムネイル切り出しAPIを用いたメモリ負荷軽減。
*   **機密性 (Security):** 外部ボリュームへのアクセス権をmacOSの `Security-Scoped Bookmark` を通じて安全にディスク保存する。
*   **簡易ロック:** 詳細設定の簡易ロックは、強固な暗号化ではなく誤操作・覗き見を抑える軽いロックとして扱う。忘失時にユーザーが回復できることを優先し、パスワード欄と解除入力欄はマスクせず通常テキストで表示し、値は `@AppStorage` に平文保存する。

## 3. アーキテクチャ設計 (System Architecture)

### 3.1 データベース設計 (Database Schema via SwiftData)

データベースエンジンには、Core Data（SQLiteバックエンド）の最新のラッパーである **SwiftData** を採用。

```
                       ┌──────────────┐
                       │    Volume    │
                       └──────┬───────┘
                              │ 1
                              │
                              │ 0..*
                       ┌──────▼───────┐
                       │     Item     │
                       └──────┬───────┘
                              │ 0..*
                              │
                              │ 0..*
                       ┌──────▼───────┐
                       │    Shelf     │
                       └──────────────┘
```

#### ① Volume (マウント・外部メディアエンティティ)
物理的なドライブ、パーティション、またはネットワーク共有フォルダを抽象化したエンティティ。
*   `id`: `UUID` [Primary Key] - 内部一意識別子
*   `name`: `String` - ユーザー向けのドライブ・フォルダ表示名 (例: "Manga HDD")
*   `lastKnownPath`: `String` - 最後にマウントが確認された絶対パス (例: `/Volumes/MangaDrive`)
*   `bookmarkData`: `Data?` - macOSのセキュア永続アクセス用のセキュリティ・スコープ・ブックマーク

#### ② Item (書籍エンティティ)
管理対象となる個々のZIPファイルまたはフォルダ。
*   `id`: `UUID` [Primary Key] - 内部一意識別子
*   `legacyID`: `Int?` [Unique Index] - Stackroomの「ID」（プレイリストのバインドに必須）
*   `volume`: `Volume?` [Relation (Optional)] - この本が属するマウントボリューム
*   `relativePath`: `String` - ボリュームルートからの相対パス (例: `Completed/Title.zip`)
*   `bookmarkData`: `Data?` - **アイテム個別のSecurity-Scoped Bookmark**（D&D登録時などファイル自体をユーザーが選択した場合に保存。解決時はボリュームより優先）
*   `title`: `String` - 書籍タイトル
*   `author`: `String` - 作者名
*   `rating`: `Int` - 5段階評価のレート (0〜5)
*   `isUnread`: `Bool` - 未読フラグ（旧XMLの `Unseen` からマッピング）
*   `pages`: `Int` - ページ数
*   `bookType`: `Int` - 書籍タイプ（単行本、同人誌、雑誌等のオリジナル数値）
*   `fileType`: `Int` - ファイルの種類（ZIP, フォルダ等のオリジナル数値）
*   `genre`: `String` - ジャンル名（旧メタデータのカスタムマッピング先）
*   `relation`: `String` - 関連作品
*   `keywordA`: `String` - 検索タグA
*   `keywordB`: `String` - 検索タグB
*   `memo`: `String` - メモ（旧XMLの `Neta` からマッピング）
*   `addedDate`: `Date` - ライブラリ登録日時
*   `lastReadDate`: `Date?` - 最終読込/プレイ日時
*   `shelves`: `[Shelf]?` [Relation (Many-to-Many, Inverse)] - 紐づくフォルダ（シェルフ）のコレクション

#### ③ Shelf (フォルダ・プレイリストエンティティ)
ユーザーが自由に編成、または条件を指定して生成する仮想本棚。
*   `id`: `UUID` [Primary Key] - 内部一意識別子
*   `title`: `String` - 本棚名
*   `icon`: `Int` - アイコンタイプ値
*   `type`: `Int` - プレイリストの種類 (0: 静的シェルフ, 1: 条件付きスマートシェルフ)
*   `sortOrder`: `Int` - サイドバー内の手動並び順。同一 `type` 内で評価し、シェルフ行のマウスドラッグで更新する。ドラッグ中はメモリ上のUUID配列だけを動かし、ドロップ完了時に一度だけ保存する。
*   `sortKey`: `String` - 本棚内での表示ソートキー
*   `sortAscending`: `Bool` - 昇順/降順
*   `smartConditionsJson`: `String?` - スマートシェルフの検索・日付条件フィルタ辞書のJSONシリアライズ文字列
*   `items`: `[Item]?` [Relation (Many-to-Many)] - 静的シェルフに所属する Item の実体リスト

### 3.2 スマートシェルフ設計 (Smart Shelf Design)

Stackroomの利用例（MacWin Ver.0.7「Stackroomで写真や漫画を管理する」2008-11-19）では、スマートシェルフは iTunes のスマートプレイリストと同じ位置づけで説明されている。ユーザーは各項目に「タイトル・作者・関連・ジャンル・キーワードA・キーワードB・メモ」などの任意メタデータを付与し、その値を条件にして写真・漫画・動画などを動的に分類する。例として、ジャンルに「街」を入れた項目を「ジャンルが街」のスマートシェルフへ自動集約する運用が示されている。

ShelfRow ではこの思想を次の仕様として継承する。

*   **メタデータ駆動の動的分類:** スマートシェルフは物理フォルダでも静的リストでもなく、Item のメタデータに対する保存済み検索条件として扱う。条件に一致するかどうかは表示時に評価し、対象Itemのメタデータ変更は即座に所属結果へ反映される。
*   **対象フィールド:** キーワード条件は `title` / `author` / `relation` / `genre` / `keywordA` / `keywordB` / `memo` を対象にする。編集UIでは「タイトル・作者・関連・ジャンル・キーワードA・キーワードB・メモ」の順に表示する。設定画面でカスタマイズされた項目名はUI表示名だけを変え、保存条件は安定した内部キー（`Title`, `Author`, `Relation`, `Genre`, `Keyword A`, `Keyword B`, `Neta`）で保持する。
*   **条件カテゴリ:** 旧アプリの利用例に合わせ、キーワード、日時、種類、レート、未読を条件カテゴリとして提供する。複数カテゴリを有効にした場合はAND評価とし、「ジャンルが街」かつ「未読」かつ「レート3以上」のような棚を構成できる。
*   **キーワード比較:** 文字列条件は「完全一致」「キーワードと一致（含む）」「キーワードを含まない」を持つ。保存値は旧互換のため `0=含む`, `1=含まない`, `2=完全一致` を維持する。大量蔵書での軽さを優先し、正規表現や全文検索インデックスは導入しない。
*   **日時条件:** 登録日・最後に読んだ日を対象に、「N日以内」「N日以上前」を評価する。日付が未設定の項目は、条件に一致しないものとして扱う。
*   **種類・レート・未読:** 種類とレートは複数選択可能な集合条件とし、未読は「ALL」または「未読のみ」の軽量な二値条件とする。レートは既存の 0〜5 評価を保持し、スマートシェルフ条件では1〜5を選択対象にする。
*   **保存形式:** `Shelf.smartConditionsJson` にはStackroom互換のトップレベルキー（`Keyword Condition`, `Date Condition`, `Type Condition`, `Rate Condition`, `Unseen Condition`）を持つJSONを保存する。将来条件を増やす場合も、既存キーの意味を変えずに追加キーで拡張する。
*   **編集導線:** 既存スマートシェルフの右クリック「編集...」は、必ず対象シェルフの現在の名前・条件を読み込んだ編集ダイアログを開く。スマートシェルフのアイコン選択UIは提供しない。既存データの `icon` 値は互換性のため保持し、新規作成時は既定値 `0` を保存する。新規作成と既存編集は同じ画面を使うが、シート提示状態は「新規/編集対象」を1つの値として保持し、`Bool` と別Optionalの更新順に依存しない。
*   **インポート互換:** 旧XMLからスマートシェルフ定義を取り込む場合は、未知の条件キーを破棄せず可能な範囲で保持・解釈する。UIで編集できない条件が見つかった場合は、互換性を壊さないよう設計段階で警告表示または読み取り専用扱いを検討する。
*   **パフォーマンス:** スマートシェルフ選択時だけ条件評価を行い、単なる選択移動やクリックでは再評価しない。表示対象リストは既存の `displayToken` キャッシュ方針に従い、検索・フィルタ・ソート・条件変更時のみ再計算する。

## 4. パス変換とマウント解決ロジック (Path Resolution Engine)

絶対パスからボリューム境界を自動検出し、サンドボックス対応の相対パス解決をおこなう。

```
[絶対パス]  "/Volumes/MangaStorage/Files/Comic.zip"
                       │
                       ▼ (解析・コンバート)
   1. Volume検出 ──► ルートパス: "/Volumes/MangaStorage" (Volumeレコード生成)
   2. 相対パス抽出 ─► 相対パス:   "Files/Comic.zip" (Itemレコード生成)
                       │
                       ▼ (再構築・アクセス時)
   1. Volume.bookmarkData を解決 ──► 現在の絶対マウントパスを取得
   2. 相対パスと結合 ─────────────► フルアクセスURLとしてファイル操作開始
```

1.  **絶対パスの分解:** 
    インポート時、パスの接頭辞が `/Volumes/VolumeName/...` であれば `/Volumes/VolumeName` をマウントポイントとして `Volume` を初期化（未作成時）。残りの `/Files/...` を `Item.relativePath` に格納。そうでない場合はシステム起動ドライブ `/` を `Volume` として処理。
2.  **実行時のセキュリティScoped解決:**
    ファイルへのアクセス時は、必ず `Volume.bookmarkData` の解決を試みる（`URL(resolvingBookmarkData:options:...)`）。取得した安全なURLに対して `startAccessingSecurityScopedResource()` を呼び出した上で、相対パスを結合してアクセスする。

## 5. サムネイルキャッシュ設計 (Thumbnail Cache Strategy)

2万件の書籍に対して、画面のスクロール追従性と省メモリを両立させるためのハイブリッドなアーキテクチャ。

```
                      getCoverImage(for: Item)
                                │
          ┌─────────────────────┴─────────────────────┐
          ▼ 1. メモリキャッシュ (RAM)                 ▼ 2. ディスクキャッシュ
      [NSCache]                                 [~/Library/Caches/.../Thumbnails/]
  (デコード済・極超高速)                                 (ファイルシステム・高速)
   ・ヒット ──► 描画                                     ・ヒット ──► NSCacheに展開 ──► 描画
   ・ミス ────┐                                         ・ミス ────┐
              │                                                    │
              └─────────────────────┬──────────────────────────────┘
                                    │
                                    ▼ 3. 物理抽出 or 旧アセット移行
                        ┌───────────┴───────────┐
                        ▼ (JIT抽出 / インポート)   ▼ (Stackroomサムネイル)
                     [ZipExtractor]       [Stackroom Library/ID/thumbnail.jpg]
                     (連番候補画像)
                        │                       │
                        └───────────┬───────────┘
                                    │
                                    ▼ 4. CGImageSource で 400px に縮小
                                    │
                                    ▼ 5. キャッシュディスクにJPEG保存 ＆ NSCache格納 ＆ 描画
```

1.  **物理コピー（インポートフェーズ）＋一括移行:**
    XMLインポート時に `item.legacyID` を手がかりに旧 `thumbnail.jpg` を `Caches/jp.aromatics.ShelfRow/Thumbnails/[item.id].jpg` へコピーする。**サンドボックス下では旧アプリフォルダへ直接アクセスできないため、`NSOpenPanel` で「Stackroom Library」フォルダをユーザーに選ばせ、security-scoped URL を経由**する。既存アイテムにも後から適用できるよう、⚙️「Stackroomサムネイルの移行...」を別途提供。
2.  **オンデマンド抽出（JITフェーズ）＋カバー選定:**
    旧サムネイルが無い場合、表示要求時にバックグラウンドでZIP/フォルダ内の画像を列挙し、`CoverSelector.preferredCoverData` により表紙データを選ぶ。基本は**「末尾の数字だけが異なる連番グループのうち最大グループの最小番号」**を採用するが、その画像がモノクロの場合は、名前順で最初の縦長かつ非モノクロ画像へフォールバックする（カラー表紙が `P001.jpg`、本文連番が `P007.png` 以降のような雑誌ZIPに対応）。破損画像は事前チェックとデコード失敗時のスキップで回避する。ZIPの読み出しは純Swiftの `ZipExtractor`（子プロセス不使用）で行う。
3.  **高速ダウンスケーリング:**
    `CGImageSourceCreateThumbnailAtIndex` APIを使用し、画像をフルピクセルで展開することなく、メモリ制限（長辺最大400px）内に収まる縮尺のサムネイルをGPUフレンドリーにデコード。
4.  **NSCache 制限:**
    RAM内のメモリキャッシュは最大200枚に制限。超過分は自動パージしOOMを防止。
5.  **一括修正（モノクロ/横長=ゴミ疑い）:**
    環境設定 > 保守の「サムネイルの一括生成...」で、キャッシュ済みサムネイルの特徴量を軽量に読み取り、**モノクロ、または横>縦のものをゴミ画像疑いとして再抽出**する。対象判定は `TaskGroup` で並列スキャンし、横長判定は画像ヘッダのみ、モノクロ判定は必要なものだけ縮小デコードする。再抽出時は連番グループの先頭画像を採用し、その画像がモノクロだった場合は、全画像を名前順に走査して最初の「縦長かつ非モノクロ」画像を採用する。未生成サムネイルは画像デコーダに渡さずスキップし、ImageIO系エラーの大量発生を避ける。
6.  **表紙の手動差し替え:**
    `CoverEditorView` でZIP/フォルダ内画像をスライダー選択し `setCustomCover` で上書き。`coverDidChange` 通知で全 `CoverImageView` が即時リロード。
7.  **壊れた画像の事前スキップ:**
    `IIOScanner::seek reached EOF` の大量出力を避けるため、JPEG/PNG/GIF/WebP は軽量なコンテナ完全性チェックを行い、明らかな途中切れ画像を `CGImageSource` / `NSImage` に渡さない。通常サムネイル生成、表紙編集プレビュー、サムネイル一括修正の特徴量判定で共通利用する。

## 6. モジュール・クラス設計 (Detailed Class Design)

### 6.1 `LibraryImporter` (バックグラウンドインポーター・ModelActor)
インメモリでXMLを安全に解析し、マルチスレッドをブロックせずにDB登録を実行する独立アクター。
*   **構造:** `actor LibraryImporter: ModelActor`
*   **プロパティ:**
    *   `modelExecutor: ModelExecutor` (SwiftDataのモデル保存実行機構)
    *   `modelContext: ModelContext` (アクターに完全に分離されたスレッドセーフなDB書き込み領域)
*   **公開API:**
    *   `importLibrary(from url: URL) async throws -> (booksCount: Int, playlistsCount: Int)`
*   **主要アルゴリズム (XMLクレンジング):**
    XMLパーサーは規格（XML 1.0）違反の制御文字（SOH: `\x01` 等）を検出するとエラーで即時停止する。アクター内部で事前に生データ `Data` を走査し、`0x00-0x08`, `0x0B-0x0C`, `0x0E-0x1F` (タブ、改行、キャリッジリターン除く) をバイパスするバイトバッファ再構築を高速実行（約10〜20ms）してからPLIST展開をおこなう。

### 6.2 `ThumbnailCache` (表紙・サムネイル解決管理アクター)
スレッドセーフなキャッシュ読み込み、ディスクキャッシュ保存、ZIP解凍連携をすべて集約した管理クラス。
*   **構造:** `actor ThumbnailCache` (グローバルアクター `@ThumbnailCacheActor` 制限)
*   **公開API:**
    *   `getCoverImage(for item: Item) -> NSImage?`
    *   `setCustomCover(forItemID:imageData:) -> NSImage?`
    *   `clearCache()`
*   **依存関係:** `ItemFileAccess` / `CoverSelector` / `ZipExtractor`

### 6.3 `ZipExtractor` (純SwiftのZIPリーダー)
*   **構造:** `nonisolated struct ZipExtractor`
*   **重要:** 旧実装は `/usr/bin/unzip` を子プロセス起動していたが、**App Sandbox では security-scoped アクセス権が子プロセスに継承されず**外部ボリューム上のZIPを読めなかった。そのため `FileHandle`＋`Compression` による純Swift実装（セントラルディレクトリ解析＋raw deflate）へ全面移行。ZIP64・日本語ファイル名（UTF-8/Shift_JIS）対応。

### 6.4 `ItemFileAccess` / `SmartConditions` (共通基盤)
*   `ItemFileAccess`: `resolve`（アイテム個別→ボリュームの順でsecurity-scoped解決）、`listPages`/`loadPageData`、`PathParser`、`CoverSelector`（連番ヒューリスティック）、`FileNameParser`（カスタムフォーマット解析＋`(ジャンル)[作者名]タイトル` フォールバック）。
*   `SmartConditions`/`SmartConditionsCodec`: スマート条件のレガシー互換JSON⇔構造体変換とAND評価、`BookTypeInfo`（種別カラー/アイコン）。

## 8. MECEな例外・エラー処理マトリクス (Exception Handling Matrix)

起こり得るエラー状態と、その発生レイヤー、回避設計を重複なく整理（MECE）。

| カテゴリ | 具体的な異常ケース | 発生レイヤー | アプリケーション側の回避・復旧設計（堅牢化設計） |
| :--- | :--- | :--- | :--- |
| **XMLインポート** | XML 1.0仕様違反の制御文字（SOH等のバイナリゴミ）の混入 | `LibraryImporter` | 事前に raw Data バッファを高速スキャンし、禁止バイト配列のみを除外してクリーンアップしてからパースを実行。 |
| **XMLインポート** | プレイリストにXML内に実在しない書籍IDが含まれている | `LibraryImporter` | インポート時に書籍キャッシュ辞書からマッチングし、存在しないIDは無視して静的シェルフの紐付けをおこなう（クラッシュ回避）。 |
| **ファイル解決** | 外付けHDDが取り外されている / パス名が変更されている | `ThumbnailCache` / `ContentView` | 物理的なファイルチェックに加え、セキュリティ・スコープ・ブックマーク解決が失敗した場合、アイテムは「未接続」状態とし赤シグナルを表示、再割り当て設定をユーザーへ即座に案内。 |
| **ファイル解決** | 書籍ファイルそのものがすでに削除・紛失している | `ContentView` / Viewer | ファイルオープン前に `FileManager.default.fileExists` で厳密確認し、欠落時はダイアログでユーザーに警告を出し、Finder遷移や不要なアプリフリーズを抑止。 |
| **キャッシュ解決** | メモリが逼迫し画像ロードによりOOM（Out Of Memory）が発生 | `ThumbnailCache` | `NSCache` のカウントリミットを 200 に設定し、超過したデコード画像は自動でメモリパージ（RAM安全域確保）。 |
| **キャッシュ解決** | ZIPファイルの最初の画像を抽出するが、破損している | `ThumbnailCache` | `CGImageSource` のサムネイル生成失敗を検知した時点で、プレースホルダー本棚画像へセーフティに縮小・フォールバック。 |

## 10. サンドボックス／セキュリティ設計 (Sandbox & Entitlements)

App Sandbox 有効を前提に、外部ストレージ・旧アプリ資産へ安全にアクセスする。

*   **Entitlements (`ShelfRow.entitlements`):** `com.apple.security.app-sandbox` / `com.apple.security.files.user-selected.read-write` / **`com.apple.security.files.bookmarks.app-scope`**。ビルド設定 `ENABLE_USER_SELECTED_FILES = readwrite`。
*   **アクセス権の永続化:** ユーザーが `NSOpenPanel` で選んだURL（ボリュームのルート、旧サムネイルフォルダ、D&Dで登録したファイル）から Security-Scoped Bookmark を生成し、`Volume.bookmarkData` または `Item.bookmarkData` に保存。解決は**アイテム個別 → ボリューム**の順。
*   **子プロセス禁止:** security-scoped 権限は子プロセスに継承されないため、ZIP展開等は必ずアプリ内（純Swift `ZipExtractor`）で実施する。
*   **外部起動時の権限保持:** 外部ヘルパー起動後、対象が開かれるまで security-scoped アクセスを一定時間（約10秒）保持してから解放する。

## 11. ビューア連携設計 (External Viewer Integration)

内蔵ビューアは持たず、**完全に外部ビューアへ委譲**する（第6期に方針確定）。

*   **設定:** 環境設定 > スライドショーに「スライドショーヘルパー」「Zip アーカイブヘルパー」を持つ。各ヘルパーは選択したアプリ名を表示するラベル＋「選択...」/「解除」で管理し、フルパスを保存。未設定時は赤文字で警告。
*   **起動ルーティング（`openItem` / `startSlideshow`）:**
    1. ツールバー/右クリック「スライドショー」→ スライドショーヘルパー。
    2. ダブルクリック/「このヘルパーで開く」→ 拡張子ヘルパー（環境設定>ヘルパー）→ `.zip` は Zip ヘルパー → 画像フォルダはスライドショーヘルパー → その他はシステムデフォルト。
    3. いずれもファイルのフルパスを外部アプリへ渡す。未設定なら案内アラート。

## 12. リスト/グリッド操作設計 (Interaction & Performance)

macOSのSwiftUI `List` の制約に対応した、実測ベースの確定仕様。

*   **選択:** `List(selection:)` は**使用しない**（内部タップ処理が独自ジェスチャと競合し単クリックが不安定化するため）。選択は手動（`selectedItemID`）で管理し、ハイライトは `.listRowBackground` で自前描画（選択行の文字色は白反転）。
*   **3ペイン幅:** サイドバーとインスペクタはユーザー調整幅を維持し、`SplitViewAutosave` が内部 `NSSplitView.autosaveName` を設定することで divider 位置を次回起動時に復元する。ウィンドウの拡大縮小は中央のリスト/グリッドビューで吸収する。ウィンドウ初期サイズは、各ペインの基本要素が隠れず表示できる最低限のサイズを基準にする。
*   **クリック:** 単クリック選択は `PrimaryClickOverlay`（最小限の `NSViewRepresentable`）で左 `mouseDown` 時に即時発火し、`event.clickCount >= 2` でダブルクリックオープンする。右クリックは `hitTest` で下層の SwiftUI `contextMenu` に通す。行/カードは `.contentShape(Rectangle())` で全面をヒット領域化。
*   **キーボード:** `ScrollViewReader` + `.focusable()` + `.onKeyPress(.upArrow/.downArrow/.return)` を自前実装（`moveSelection` が選択移動＋自動スクロール、Enterで開く）。
*   **パフォーマンス:** フィルタ＋ソート結果を `@State displayItems` にキャッシュし、`displayToken`（サイドバー選択・検索・各フィルタ・ソート・件数の合成文字列）が変化した時のみ再計算。選択操作では再計算しない。
*   **リストのカラムヘッダー:** クリックでソート（▲▼）、右クリックで列の表示/非表示（`@AppStorage("listVisibleColumns")` に永続化、タイトル列は常時表示）。
*   **アイテム右クリックメニュー:** スライドショー/このヘルパーで開く/削除/ゴミ箱に入れる/レート/種類/未読チェック/Finderで表示/ファイルを移動/リネーム/表紙を編集/ファイルを再指定/並び替え。

## 13. データ補完・整備機能 (Data Repair Utilities)

### 13.0 起動時3世代自動バックアップ (Startup Backup)

論理的なデータ破壊から素早く回復するための自動バックアップ。ユーザー操作不要で毎回の起動時に実行される。

*   **実装:** `ShelfRowApp.swift` 内の `private enum SwiftDataStartupBackup`。`sharedModelContainer` の初期化クロージャ冒頭で、`ModelContainer(for:)` を呼ぶ**直前**に実行する。SwiftData がDBをロックする前のタイミングを意図的に選んでいる。
*   **対象ファイル:** `default.store` / `default.store-wal` / `default.store-shm`（SQLite WAL モードの3ファイル）。3ファイルをセットでコピーすることで、チェックポイント前のWALを含む完全な状態を保持する。
*   **保存場所:** `Application Support/StartupBackups/gen0〜gen2/`（コンテナ内部、外部ボリューム不要）。
*   **世代ローテーション:** 起動ごとに最古の `gen2/` を削除 → `gen1/` → `gen2/`、`gen0/` → `gen1/` とシフト → 現在のストアを `gen0/` へコピー。各世代に `backup_date.txt`（ISO 8601）を書き込む。
*   **安全設計:** 失敗はすべて無視。初回起動時（ストアファイル未存在）はスキップ。
*   **リストア手順:** アプリを終了 → `Application Support/` の `default.store*` を `StartupBackups/gen1/` または `gen2/` の内容で手動上書き → 再起動。
*   **既存バックアップとの役割分担:** 環境設定 > 保守のバックアップはユーザー選択の外部フォルダへDB全体＋サムネイル＋設定を差分コピーする意図的な保全操作。起動時バックアップはコンテナ内部限定の最終手段として独立して機能する。

環境設定 > 保守から実行する一括処理群。

*   **XMLライブラリのインポート...:** Stackroomの `Stackroom Library.xml` を読み込み、既存データへマージする。
*   **Stackroomサムネイルの移行...:** 旧 `Stackroom Library` フォルダを選び、legacyID を持つ全アイテムのサムネイルを一括コピー（再実行可）。
*   **環境設定 > 保守:** バックアップ設定、ボリューム管理、XMLライブラリのインポート、Stackroomサムネイルの移行、サムネイルの一括生成、ファイル名からタイトルを補完を集約する。各ボタンには読みやすい大きさの説明文を併記し、ボタン押下時は `NotificationCenter` 経由または保守ペイン内の専用処理で実行する。未実装扱いだった「エイリアスの復元」はUIから削除する。
*   **サムネイルの一括生成...:** 既存キャッシュファイルがあるサムネイルだけを対象に特徴量確認し、モノクロまたは横長サムネイル（ゴミ疑い）を再抽出。対象判定はバックグラウンド並列スキャンで行い、対象外アイテムではファイル解決やZIP抽出へ進まない。連番グループの先頭画像を採用し、その画像がモノクロなら、名前順で最初の縦長かつ非モノクロ画像にフォールバックする。未生成サムネイルはスキップして不要な ImageIO エラーを出さない。
*   **ファイル名からタイトルを補完...:** 環境設定のカスタムフォーマットを `FileNameParser` で解析し、空欄のタイトル/作者/ジャンル/関連/キーワードA/Bを補完し、`@type` が種類名に一致すれば種類も更新する。書式不一致時は従来の `(ジャンル)[作者名]タイトル.zip` 規則へフォールバック（**先頭の `()` `[]` のみ採用、末尾 `[]` は無視**）。D&D新規登録でも同解析を適用。
