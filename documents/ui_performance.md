# 大規模ライブラリのUI・I/O高速化（2026-09-22）

## 対象と観測

本番ライブラリ19,287件を対象に、画面更新、キーボード移動、サムネイル、NAS配布、CloudKit進捗、起動時処理、バックアップ、ファイル操作をコード全体から確認した。

この端末で観測した規模は次のとおり。

- `Item`: 19,287件
- 端末ローカルの表紙状態: 19,218件
- 端末ローカルのサムネイル: 約809 MB
- 旧方式で起動時に複製対象になっていたSQLite WAL: 最大約1.13 GB
- 端末ローカルのセキュリティスコープブックマーク: 38件

変更前の連続選択中に6秒間の `sample` を採取すると、メインスレッドに `ContentView.sidebarPane` と `shelfItemCount` が繰り返し現れた。変更後の同様の操作ではこの集計経路は現れなかった。これは不要な処理経路を除去できたことの確認であり、FPSや操作遅延の厳密なベンチマークではない。

## 一覧表示と検索

- SwiftDataの `@Query` は全件を一度取得するだけとし、画面の `body` から検索、フィルタ、ソート、シェルフ件数集計を外した。
- `LibraryItemSnapshot` というSendableな値を作り、専用actorで検索、自然順ソート、通常／スマートシェルフの判定、件数集計を行う。SwiftDataモデルを別actorへ渡さない。
- 19,000件分のスナップショット作成中は64件ごとにyieldし、メインアクターを長時間占有しない。
- データ世代番号を持ち、検索語、表示シェルフ、並び順だけが変わった場合はモデル全件を読み直さず、既存スナップショットを再利用する。
- 1件の属性編集ではその `Item` のスナップショットだけを差し替える。追加、削除、シェルフ構造変更、CloudKitのリモート変更時だけ全件を再構築する。
- `LocalBookmark` と `LocalCoverState` の保存通知は一覧に関係しないため、全件再投影を起こさない。
- 入力と保存通知は120 msまとめ、新しい要求が来たら古いTaskをキャンセルする。走査とソート中もキャンセルを確認し、古い結果を画面へ反映しない。
- 初回だけ読み込み表示を出す。再検索中は現在の一覧を残し、右上に小さな更新表示を出して操作を継続できるようにした。
- 選択状態を独立した `@MainActor @Observable` 状態にし、サイドバー、一覧、インスペクタの更新境界を分けた。
- リスト行を `LibraryListRow` に分離し、SwiftData属性の観測範囲をその行に限定した。行番号とIDを値で保持し、全行でモデルIDを繰り返し読む処理も除いた。
- 列定義と種別名配列は行ごとに作らず、親ビューで一度だけ作って共有する。

## 属性編集と登録

- インスペクタのテキスト属性は編集中の値をローカルdraftに置く。文字を1文字入力するたびにSwiftDataへ保存せず、Return、フォーカス移動、画面離脱時にまとめて反映する。
- 複数ファイルのドラッグ＆ドロップは、ファイル種別確認をメインアクター外で行う。既存アイテムとボリュームを辞書化し、ファイルごとのSwiftData検索をなくした。
- ドロップした各ファイルのブックマークを個別保存せず、全件登録後に1回だけ保存する。
- NAS上のファイルの移動、名称変更、ゴミ箱への移動はバックグラウンドで行い、その間は進捗状態を表示する。セキュリティスコープは処理完了まで保持する。
- 旧サムネイル移行、破損／横長／モノクロ表紙の検査、表紙生成はバックグラウンドで実行し、変更されたIDのキャッシュだけを無効化する。

## キーボード移動とスクロール

- キーフォーカスをスクロール内容の外側にある安定したコンテナへ置いた。
- 選択からスクロールへの要求を片方向にし、`scrollPosition` の双方向更新が末尾で選択位置を上書きする経路を廃止した。
- 末尾や先頭で同じ方向のキーを押し続けた場合は、選択を変えないままキーを処理する。次の逆方向キーは直ちに移動できる。
- キーリピート時のスクロールアニメーションを無効化し、LazyVStackの最小移動だけで選択行を表示する。
- 選択行にアクセシビリティの選択済み特性を付け、VoiceOverとUIテストの双方が状態を直接認識できるようにした。

## サムネイル表示とキャッシュ

- メモリキャッシュは同期参照できる `NSCache` とし、既にデコード済みなら同じ描画フレームで表示する。
- ディスク上のJPEGはバックグラウンドの並列読み込みキューで即時デコードし、長辺を最大768 pxに制限する。元ファイルは変更しない。
- 画面で必要な表紙読み込みを、先読みや原本抽出と同じ直列actorに並ばせない。ディスク読み込み、原本／NAS抽出、NAS一括転送にそれぞれ専用キューを用意した。
- 選択先読みはキー移動が250 ms止まってから近隣だけを対象にする。原本やNASへは進まず、端末内にあるレンダリング済み画像だけを温める。
- 同じIDの同時要求は1つのTaskへまとめ、同じ書籍を二重に展開しない。
- 到達不能なNASを「表紙なし」として負キャッシュしない。NASが戻れば再試行できる。
- キャッシュディレクトリURLを毎回作成せず、一度だけ解決する。
- 一部の表紙が変わった場合にメモリキャッシュ全体を捨てず、該当IDだけを無効化する。
- 一括表紙生成は構造化TaskGroupで最大8件を進める。ブロッキングするアーカイブ／NAS処理はSwiftの協調実行プールから専用I/Oキューへ逃がす。

## NASサムネイル配布

- ローカルキャッシュはディレクトリを1回列挙して `[UUID: byte数]` のinventoryを作る。19,000件を1件ずつ `fileExists` で確認しない。
- 自動同期1回につき、ローカル表紙状態、Item ID、キャッシュinventoryを各1回取得し、採用、孤立行削除、アップロード計画、ダウンロード計画に再利用する。
- 計画直後の転送へ対象配列をそのまま渡し、転送開始時の全件再走査をなくした。
- CloudKitの保存通知が連続しても2秒まとめて1回だけ計画する。起動時は最初の画面描画を優先し、配布元確認後5秒待って開始する。
- NASのmarker／manifest読み込み、配布元検証、manifest書き込みをメインアクター外へ移した。
- サムネイルの転送は `Data(contentsOf:)` と `Data.write` でファイル全体を二重保持せず、`FileManager.copyItem` でストリームコピーする。
- NASはUUID先頭2文字の小文字shardに分ける。一度確認したshardは記憶し、ファイルごとのディレクトリ作成要求を避ける。
- 転送は既定6並列（設定範囲2〜16）で、Swift協調実行プールとは別のI/Oキュー上で行う。
- manifestにない表紙をNASへ問い合わせない。未登録19,000件に対する不要なSMB往復を防ぐ。

## 起動、DB、CloudKit

- 起動のたびにSQLite本体、WAL、SHMを同期コピーする旧バックアップを廃止した。約1.13 GBのWALがある環境でも最初のウインドウ表示と競合しない。
- 起動30秒後、かつ前回から24時間以上経過した場合だけ、SQLite Backup APIでトランザクション整合性のあるスナップショットを作る。最大3世代を保持する。
- 旧形式の巨大なWAL／SHMコピーを含むバックアップは、有効な新スナップショット作成後に整理する。
- iCloudモード切り替え前のバックアップもSQLite Backup APIでメインアクター外に作成する。成功するまでローカルDBを消さず、次回起動時の重複バックアップも避ける。
- CloudKit未送信件数のSQLite private metadata照会をバックグラウンドで行う。端末内件数はModelActorで `fetchCount` し、同じ値ならUI状態を書き直さない。
- 未送信件数の5秒監視は環境設定の同期画面を表示している間だけ動く。
- 使用できないprivate schemaは起動中に何度も再照会せず、1回失敗したらCloudKitイベントによる状態判定へ戻る。

## 除去・維持した処理

- 未使用だった単一削除関数と、キーワード選択後の重複した明示更新を削除した。
- ファイルを開く時の存在／権限確認、ユーザーが明示実行するバックアップ／リストア、初回だけの旧ブックマーク移行は正当な処理として維持した。
- CloudKitのProduction接続、同期対象モデル、NAS上の実体ファイル、端末ローカルにだけ置くサムネイルという構成は変更していない。

## 検証

全ユニットテスト67件が成功した。うち性能・同期の主要対象23件は次を含む。

- 20,000件の投影、キャッシュ再利用、自然順、昇順／降順、通常／スマートシェルフ、件数集計
- 全角・アクセント・同義語検索、属性更新、削除、条件変更、キャンセル
- 画像の最大768 pxデコードと元ファイル不変
- キーボードの上下端反転、グリッド移動幅
- 起動バックアップの24時間抑制
- NAS manifest、shard、ラウンドトリップ、途切れた転送、転送並列数、ローカルモード時の停止

20,000件の値スナップショットを使う投影テストでは、この実行時にcold約33 ms、同じデータ世代を再利用するwarm約15 msだった。これはUI全体のフレーム時間ではなく、actor上の検索・フィルタ・自然順ソート・件数集計部分だけの参考値である。

署名付きDebugアプリを使うUIテストも成功した。36行を画面外までDownで進み、末尾でさらにDownを繰り返した直後にUpで34行目へ戻る。その後先頭までUpを繰り返し、直後のDownで1行目へ進むことを実キーイベントで確認している。

保存通知はプロセス全体に配信されるため、現在表示中のライブラリと同じModelContainerからの通知だけを一覧更新に使う。これにより独立した一時コンテナの識別子を誤って解決する問題も除去した。Debugビルドと全ユニットテストは成功し、アプリのコンパイル警告はない。

## ビルドと成果物

通常のRelease確認は次で行う。

```sh
xcodebuild -project ShelfRow.xcodeproj -scheme ShelfRow -configuration Release \
  -destination 'generic/platform=macOS' \
  -derivedDataPath /private/tmp/ShelfRowPerformanceRelease \
  build CODE_SIGNING_ALLOWED=NO
```

配布用のDeveloper ID署名、ZIP作成、署名検証は `./script/build_and_run.sh --build-only` を使う。引数なし／`--verify` は既存のShelfRowを終了して起動するため、実行中の作業がある場合は `--build-only` を使用する。本性能対策では公証提出、コミット、pushは行わない。
