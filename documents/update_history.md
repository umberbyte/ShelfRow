# ShelfRow 開発・更新履歴 ＆ AI引き継ぎ仕様書 (Update History & Handoff Document)

本ドキュメントは、レガシーmacOSアプリ「Stackroom」を現代の環境（SwiftUI / SwiftData）に移植・新生するプロジェクト「ShelfRow」において、これまでに実施された全設計変更、発見された重要技術仕様、および現在のソースコード構成を、**後続のAIまたは開発者が完全に理解し、即座に作業を引き継げるよう極めて詳細に記録した履歴書**である。

> 運用ルール: 今後、機能・挙動・データ構造・重要な不具合修正を変更した場合は、コード修正と同じタイミングで `documents/update_history.md` と `documents/design_document.md` を更新する。

## 1. 開発マイルストーン ＆ 変更履歴 (Milestones & Change Log)

これまでの開発は、単なる「モダンなリライト」から始まり、ユーザーからの詳細なフィードバックを経て「旧アプリのUI・アセットを極限まで引き継ぐ完全移植」へと進化を遂げた。以下にその全軌跡を記録する。

### 📅 第18期：iCloudへの全件再送信と、置き換え時のストア削除の修正
*   **背景:** 1台目は「未送信 0件 / 送信済み 19,238件」と表示しているのに、2台目が37件しか受け取らずに止まった。原因は CloudKit ミラーリングがレコードごとに持つ送信済みフラグ（`ANSCKRECORDMETADATA.ZNEEDSUPLOAD`）が、**Development 環境での完走時に全件 0 になり、Production への切り替えでリセットされなかった**こと。Production の DB は空なのにローカルは全件送信済みと認識しており、送るものが無い状態だった。
*   **ゾーン削除では回復しない:** ゾーンの消失を検知した CoreData は関連（CDMR）のミラーリング状態だけを無効化する。レコード本体のフラグは残るため、関連レコード 19,217件だけが再送され、書籍レコードは 1件も上がらなかった。2台目は参照先の無い関連を抱えて取り込みを無限に再試行していた。
*   **実装:** `ShelfRow/CloudResend.swift` の `CloudResender`（`@ModelActor`）。200件ずつ「一時的な値で保存 → 元の値に戻して保存」の2段階で全オブジェクトを書き換え、送信待ちフラグを立て直す。iCloud に届く内容は現在の蔵書そのままで、変わるのはフラグだけ。環境設定 > iCloud の「iCloudへ全件を再送信」から実行する。
*   **書き換える属性の選び方:** 途中でクラッシュすると一時的な値が残るため、読まれても害の無いものだけを使う。`Item.bookmarkData` / `Volume.bookmarkData` はブックマークをローカルストアへ移した時点から誰も読まない死んだ列。`Shelf.sortOrder` と `CoverExtractionRecord.updatedAt` は元に戻る。
*   **併せて修正:** 「iCloudの蔵書で置き換える」の再起動で `vnode unlinked while in use` が出ていた。再起動は新インスタンスを先に起動して旧インスタンスを後で終了させるため、削除の時点で旧プロセスがまだストアを開いている。`LibraryStore.waitForOtherInstancesToExit()` で同一バンドルIDの他プロセスが消えるまで最大10秒待ってから削除する。
*   **端末の役割を記録する（`libraryCloudRole`）:** 同期をオンにしたとき「1台目（`primary`）」「2台目以降（`replica`）」のどちらを選んだかを保存し、2台目以降では「iCloudへ全件を再送信」と「iCloudのデータを削除」を非表示にする。どちらも全端末に及ぶ操作であり、iCloud の内容を作った端末のものだから。蔵書を iCloud から受け取っただけの端末では、他の端末の成果を壊す手段にしかならない。現在のモード表示にも「2台目以降」と出して、項目が無い理由が分かるようにした。記録が無い端末（この仕組みより前から同期していた1台目）は `primary` 扱いとし、既にあったものを隠さない。iCloud のデータを削除したら役割も消し、次回オンにしたときに選び直させる。
*   **教訓:** Development で同期を検証してから Production に移すことはできない。送信済みフラグが持ち越されるため、切り替え直後の全件再送信が必須。「未送信 0件」はサーバ到達の証明ではなく、ローカルの記録でしかない。

### 📅 第17期：縮小表示（狭い画面向け）
*   **背景:** 画面の狭いMacでは現行UIが大きすぎ、中央の一覧に回せる幅が足りない。
*   **実装:** 環境設定 > 一般に「表示を縮小」を追加。オンで左右のペイン、上部ツールバー、書籍リストの行・列幅・ヘッダ、グリッドのカードと間隔をまとめて 75% に縮める。
*   **`DisplayMetrics` の 3 段階倍率:** `size()` 75%（アイコン・コントロール高・ラベル幅・列幅・カバー画像）、`space()` 55%（一般の余白）、`rowSpace()` 40%（行ごとに繰り返す padding）。狭い画面で場所を食っているのは文字やアイコンの大きさではなく余白であり、とりわけ行ごとに繰り返される padding が効くという判断による。`font()` は 75% だが 9pt 下限。
*   **効果:** 同じウィンドウで一覧に表示できる行数が約 24 行から約 38 行に増えた（実測）。グリッドは 6 列から 7 列に増える。
*   **ペイン幅とウィンドウ最小幅も連動:** 縮小した中身に対して幅だけ据え置くと、保存済みスプリッタ位置のせいで余白の中に浮いてしまう。最小幅は 1160 固定をやめ、両ペインの最小幅＋中央 620 から算出する。

### 📅 第16期：同期表示を「回転アイコンと完了」だけに簡素化
*   **背景:** 第14期で入れた進捗バーは、実用上ほぼ常に 100% を指すだけで意味を持たなかった（メタデータの行はキュー投入時に全件作られ、送信済み件数もすぐ総数に追いつく）。
*   **変更:** プログレスバー・百分率・件数（M/N）・送受信回数・経過時間をすべて削除。非公開スキーマを読む `CloudSeedProgress.swift` ごと削除した。残す表示は「同期中かどうか」だけ——イベントが届いている間は回転アイコン、最後のイベントから 90 秒途切れたら「送受信完了」。
*   **実装:** `isSyncing` を計算プロパティから保存プロパティに変更し、イベントのたびに 90 秒後の解除タスクを貼り直す。時刻との比較をやめたことで、画面を定期ポーリングして再描画させる必要も無くなった。
*   **副次効果:** 非公開スキーマへの依存が無くなり、OS アップデートで壊れる箇所が一つ減った。

### 📅 第15期：iCloudのデータを完全に削除するボタン
*   **目的:** アプリの利用をやめるときに iCloud の容量を完全に解放できるようにする。環境設定 > iCloud に「iCloudから完全に削除...」を追加。
*   **動作:** コンテナのプライベートDBにある既定ゾーン以外のゾーンをすべて削除する。ゾーン名をハードコードせず全列挙するのは、コンテナがこのアプリ専用でそこにあるものは全部自分のものだから。この端末の蔵書・サムネイル・設定は残り、iCloud 同期はオフになる。
*   **ミラーリング中に消してはならない:** cloud モードのままゾーンを消すと、CloudKit はゾーンの消失を検知してライブラリ全体を再アップロードする。第11期の「置き換え」と同じく削除予約フラグ（`libraryPendingCloudPurge`）を立てて再起動し、**ローカルモードで開いた状態で**削除を実行する。
*   **他端末への注意:** 他の端末で同期がオンのままだと、その端末が同じ内容を再アップロードする。確認ダイアログに「先にすべての端末で同期をオフにしてください」と明記。
*   **検証:** ボタンと確認ダイアログの表示・キャンセルを実機で確認。**削除自体は未実行**（実行するとアップロード済みの19,287件が消えるため）。

### 📅 第14期：同期の進捗表示と、テストが実ライブラリを開く問題の解消
*   **進捗バー:** 環境設定 > iCloud に「同期の進行」を追加。`CloudSeedProgressReader` がストアと同じ SQLite ファイルを読み取り専用でもう一度開き、`ANSCKRECORDMETADATA` の `ZNEEDSUPLOAD = 0` の行数を数えて「M / N 件」と百分率を出す。
*   **なぜ非公開スキーマを読むのか:** `NSPersistentCloudKitContainer.Event` は開始/終了時刻・成否・エラーしか持たず、レコード件数を一切公開しない。残り件数が書かれている場所は他に無い。利用者の判断で「OSアップデートで壊れたら作り直す」方針を採用。テーブル名・列名はパターン照合で探索し、失敗時は nil を返して「送受信の回数と経過時間」だけの表示にフォールバックする。
*   **`COUNT(*)` では駄目だった:** メタデータの行はオブジェクトがキューに入った時点で全件作られるため、エクスポートが毎分23バッチ動いている最中でも 100% と表示された。実際に送信済みかどうかを持つのは `ZNEEDSUPLOAD` フラグ。
*   **テストが実ライブラリを開いていた:** このスキームはアプリ自身をテストホストにするため、`xcodebuild test` のたびにアプリが起動して実ストア（19,287件）を開き、同期有効時は CloudKit にも接続していた。テストが作る別コンテナと衝突し、`NSInternalInconsistencyException: 'No eligible connection available'`（`try` で捕捉できない Objective-C 例外）でテストホストが落ちていた。`LibraryStore.init()` が `XCTestConfigurationFilePath` を見て、テスト実行時はインメモリのストアで起動するようにして解決。利用者のデータを無用に開かなくなる副次効果もある。
*   **`BookmarkVault` がコンテナを保持:** コンテキストだけでは `ModelContainer` の生存を保証できず、解放後の保存が例外になる。

### 📅 第13期：モード切替のホットスワップを廃止し再起動方式へ
*   **症状:** 環境設定で iCloud 同期をオンにした瞬間にクラッシュ。`SwiftData/BackingData.swift:888: Fatal error: This model instance was destroyed by calling ModelContext.reset and is no longer usable.`（`Item.id.getter`）。
*   **原因:** 実行中に `ModelContainer` を差し替えると古い `ModelContext` が reset され、そこに属する `Item` インスタンスは以後触れた瞬間にトラップする。ルートビューに `.id(generation)` を付けて木を作り直すだけでは足りない——SwiftUI は同じ更新の中で古いビューの body を再評価することがあり、プリフェッチ等の実行中 `Task` も古いモデルを保持している。
*   **対処:** ホットスワップを廃止。モード変更は「設定を書く → 自動再起動 → `LibraryStore.init()` が最初から正しいモードで開く」に一本化した。全参照が確実に消えている瞬間は最初のコンテナができる前しかない。§9 の「iCloud の蔵書で置き換える」が再起動を要求するのと同じ理由で、機構も共有する。
*   **アカウント状態の変化では自動再起動しない:** サインイン/アウトで勝手にアプリが落ちるのは乱暴なので、`restartRequired` を立てて設定画面にバナーと [今すぐ再起動] を出すに留める。次回起動時には自動的に正しいモードになる。
*   **設計書の更新:** §5.4 を書き換え、FR3（「再起動なしで切り替えられる」）を撤回。未決事項 Q3 は「不採用」で解決。

### 📅 第12期：プッシュ通知のエンタイトルメント修正
*   **症状:** `ShelfRow.entitlements` に書いた `aps-environment` が署名済みバイナリから無言で消えており、CloudKit のサイレントプッシュが届かない状態だった（他端末の変更の取り込みが起動時・フォアグラウンド復帰時に限られる）。
*   **原因:** **キー名が iOS 用だった。** macOS のプッシュエンタイトルメントは `com.apple.developer.aps-environment`。プロビジョニングプロファイルを復号して確認したところ、プロファイル側は最初から `com.apple.developer.aps-environment = development` を付与しており、こちらが要求したキーと一致しないため署名時に捨てられていた。
*   **対処:** キー名を修正。値は開発署名で `development`、Developer ID / App Store で `production` である必要があるため、ビルド設定 `APS_ENVIRONMENT` をターゲットの Debug = development / Release = production に定義し、entitlements からは `$(APS_ENVIRONMENT)` として参照する。
*   **確認:** `codesign -d --entitlements` で `com.apple.developer.aps-environment = development` が署名済みバイナリに入ることを確認済み。
*   **教訓:** エンタイトルメントは書いただけでは入らない。プロファイルが付与していないキーは警告なく削除されるので、`codesign -d --entitlements` での実機確認が必須。

### 📅 第11期：2台目の接続方式を「マージしない」に確定
*   **決定:** 2台の蔵書を突き合わせるマージは実装しない。1台目が iCloud へ送り、2台目以降は**ローカルの蔵書が消える旨を警告したうえで** iCloud の内容に置き換える（設計書 D12 / §9）。
*   **UI:** 環境設定 > iCloud のスイッチをオンにすると確認ダイアログが出る。「この端末の蔵書を iCloud へ送る（1台目）」「iCloud の蔵書で置き換える（2台目以降、破壊的）」「キャンセル」の3択。すでに iCloud に蔵書がある状態で「1台目」を選ぶと二重登録になる旨もダイアログ本文に明記。
*   **重要な実装判断:** 置き換えを `modelContext.delete` で行ってはならない。cloud モード中のレコード削除は iCloud へ伝播し、**全端末の蔵書を消す**。ストアファイル（`default.store*` / `local.store*`）ごと削除し、空の状態で iCloud へ接続して降ってくるのを待つ。
*   **再起動を挟む理由:** ストアファイルの削除は、それを開いているコンテナが無い瞬間にしか安全に行えない。削除予約フラグを立てて `NSWorkspace.openApplication` で自動再起動し、`LibraryStore.init()` が最初のコンテナを作る前に削除する。直前に `ModeSwitchBackups/` へスナップショットを取る。
*   **副作用:** 置き換えた端末では Security-Scoped Bookmark も消えるため、ボリュームのアクセス権の再設定が必要（iCloud 側の Volume は別 UUID なので残しても対応づかない）。サムネイルキャッシュは Caches 配下なので残る。

### 📅 第10期：マルチデバイス同期 Phase 1（iCloud対応の土台）
*   **実施内容:** `documents/multi_device_sync_design.md` の Phase 1 を実装。書誌メタデータを CloudKit で同期できる形にし、端末固有のデータを分離した。iCloud 同期はまだ一度もオンにしていない（ローカルモードで動作中）。
*   **モデル:** CloudKit は一意制約を持てず全属性にデフォルト値を要求するため、`Item` / `Volume` / `Shelf` / `CoverExtractionRecord` から `@Attribute(.unique)` を外し、宣言側デフォルト値を付けた。`legacyID` の一意性は `LibraryImporter` の fetch-before-insert が元から担保している。Phase 2 用に `Item.coverVersion` / `coverBytes` を先行追加（CloudKit スキーマは後から削除できないため）。
*   **ブックマークの分離:** Security-Scoped Bookmark を同期させると、各端末が解決できない他端末のブックマークで上書きし合う。`LocalBookmark`（同期しない第2ストア `local.store`）へ移し、`BookmarkVault` の辞書キャッシュ経由で読むようにした。`Item.bookmarkData` / `Volume.bookmarkData` は**削除せず残し**、初回起動時に中身を移して `nil` にする——属性を消すと軽量マイグレーションが既存データごと捨てるため。全端末がこのバージョンを起動した後のリリースで削除してよい。
*   **モードの場合分け:** 設定スイッチとアカウント状態の両方が揃ったときだけ cloud。未サインイン時は CloudKit 抜きでストアを開くので、サインアウトで CloudKit がローカルを消す経路に入らない。ストアファイルは同一で開き方だけ変えるため、オフ→オンで再アップロードにならず未送信分も失われない。切替は再起動なし（`generation` でビュー階層を作り直す）。
*   **クラッシュの原因と対策:** `CKContainer(identifier:)` は一致するコンテナエンタイトルメントが無い実行ファイルで**エラーではなくトラップ**する（署名なしビルドで必ず起動直後にクラッシュ）。`SecTaskCopyValueForEntitlement` で権限を確認してから CloudKit に触れる `CloudKitEntitlement` を追加した。
*   **検証:** 実ライブラリ 19,287 件のスキーマ移行成功、ブックマーク 37 件の移行と再起動後の読み戻しを確認。設定「iCloud」タブで状態「利用可能」とアカウント ID 表示を確認。**iCloud 同期のオン、2台目での受信、Developer ID での公証は未検証。**
*   **既知の課題:** §9「両側非空」のマージは未実装（第11期で「マージしない」方針に確定）。プッシュのエンタイトルメントが署名時に剥がされる問題は第12期で解決。

### 📅 第9期：マルチデバイス同期の設計（未実装）
*   **実施内容:** Mac 複数台 + iPad でのデータ共有方式を検討し、設計書 `documents/multi_device_sync_design.md` を作成。コード変更なし。
*   **確定した前提:** 利用者 1 人・同時編集なし／iPad はほぼ閲覧専用（編集は属性のみ）／実体ファイルは NAS／書誌メタデータと設定は iCloud 可／サムネイル等のキャッシュはクラウドへ上げず端末ごとに保持。
*   **採用方式:** SwiftData + CloudKit（プライベート DB）。検討して不採用にした NAS ジャーナル方式・DB 丸ごと同期・NAS 上サーバ方式の採否理由も設計書 §2 に記録。
*   **主要な設計判断:** (1) 未サインイン時はローカル構成でストアを開き、サインアウトによるローカルデータ削除経路を回避。(2) 環境設定「iCloud」タブのスイッチで ON/OFF を往復可能（同一ストアファイルの開き方だけを変える）。(3) ブックマークとサムネイル取得状態は非同期のローカル専用ストアへ分離。(4) サムネイルは NAS 配布元から取得し、差分検出は `Item.coverVersion` を使う。初回は容量警告つき一括、以降は差分。
*   **API 上の制約:** iCloud のメールアドレス・氏名はアプリから取得不可（`discoverUserIdentity` 系は macOS 14 で廃止）。設定画面にはユーザーレコード ID とシステム設定への導線を表示する。
*   **次の作業:** Phase 1（モデル改修 → `LibraryStore` → 設定タブ → アカウント監視）。着手前に Developer ID + iCloud エンタイトルメントの署名・公証を検証する。

### 📅 第8期：起動時3世代自動バックアップ
*   **実施内容:** SwiftDataの論理破壊に備えた起動時自動バックアップ機能を実装。`ShelfRowApp.swift` に `SwiftDataStartupBackup` を追加。
*   **動作:** アプリ起動ごとに、`ModelContainer` がデータベースを開く**直前**に `default.store` / `default.store-wal` / `default.store-shm` を `Application Support/StartupBackups/` 内へコピーする。直前に実行することで、SwiftDataがWALをロックする前の最もクリーンな状態でバックアップを取得できる。
*   **世代管理:** `gen0/`（最新）・`gen1/`・`gen2/`（最古）の3フォルダをローテーション。起動ごとに最古世代を削除し、残りをシフトして現在の状態を `gen0/` へコピーする。各世代には `backup_date.txt`（ISO 8601タイムスタンプ）を書き込む。
*   **安全設計:** バックアップ失敗はすべて無視（`catch` で吸収）し、起動を絶対にブロックしない。初回起動時（ストアファイル未存在）はスキップする。
*   **リストア手順:** アプリを終了 → `Application Support/` の `default.store*` を `StartupBackups/gen1/` または `gen2/` の内容で手動上書き → 再起動。

### 📅 第6期：外部ビューア専業化・実データ運用での不具合修正・パフォーマンス改善（試行錯誤の記録）

実機の2万件ライブラリで運用したところ、サンドボックス・ファイル操作・UIの各層で多数の問題が顕在化した。ユーザーとの対話的なデバッグを通じて以下を順に解決した。**同じ問題に再び時間を溶かさないよう、外した仮説と誤った修正も含めて記録する。**

#### 6.1 サンドボックス／ファイルアクセス権
*   **症状:** ファイルを開こうとすると「アクセス権がありません」。
*   **原因:** App Sandbox が有効なのに entitlements ファイルが無く、`com.apple.security.files.bookmarks.app-scope` が欠落。そのため `VolumeRelocationView` のブックマーク生成が例外を投げていた（`print` のみで握り潰し）。旧サムネイルの一括コピーも、サンドボックス下では `NSHomeDirectory()` がコンテナ内を指すため実際には動いていなかった。
*   **対処:** `ShelfRow.entitlements` を新規作成（app-sandbox + user-selected.read-write + **bookmarks.app-scope**）し両構成へ接続。`ENABLE_USER_SELECTED_FILES` を readonly→readwrite に。`VolumeRelocationView` はブックマーク保存失敗をアラート表示。XMLインポートは「Stackroom Library」フォルダを `NSOpenPanel` で選ばせ、security-scoped URL を `LibraryImporter` に渡す方式へ。
*   **追加対処（アイテム個別ブックマーク）:** D&D登録ファイルは `Item.bookmarkData`（新規プロパティ）に個別のsecurity-scopedブックマークを保存し、`ItemFileAccess.resolve` はアイテム個別→ボリュームの順で解決。再ドロップで既存アイテムの権限も修復可能に。

#### 6.2 「同じ作者のファイルだけ開けない」→ 実はクリック判定の問題（外した仮説を含む）
*   **当初の仮説（誤り）:** 「その作者の作品だけ別ボリュームにあり、アクセス権が未保存」。→ 診断情報アラートを実装したが、ユーザー環境では**同一ボリューム**で、しかもアラートすら出なかった。
*   **判明した真因:** リスト/グリッド行が**行全体をヒット領域にしておらず**、列と列の透明な隙間をクリックすると `onTapGesture` が発火せず `openItem` が呼ばれていなかった（作者でソートして連続クリックしていたため「作者依存」に見えていた）。加えて、複数の `.alert` を同一ビューに重ねていたため「アクセスできません」アラートが SwiftUI に握り潰されていた（別ビュー `.background` に退避して解決）。
*   **対処:** 全行/カードに `.contentShape(Rectangle())` を付与。ダブルクリック判定の取りこぼしも修正。

#### 6.3 内蔵ビューアの撤廃と外部ビューア専業化
*   **方針変更:** 内蔵スライドショービューアを廃止し、完全に外部ビューア依存へ。`SlideshowViewerView.swift` を削除。
*   **設定の整理:** 「別のビューアを使用する」チェックボックス（`slideshowUseCustomHelper`/`zipUseCustomHelper`）を全廃。内蔵ビューア専用だった「ループ」「ページ方向」設定も削除。ヘルパー欄は編集可能テキストフィールドをやめ、**選択したアプリ名を表示するラベル＋「選択...」＋「解除」**方式に。未設定時は赤文字で設定を促し、開こうとした際も案内アラートを表示。
*   **起動フロー:** スライドショーボタン=スライドショーヘルパー、`.zip`=Zipヘルパー、画像フォルダ=スライドショーヘルパー、その他=拡張子ヘルパー→システムデフォルト。いずれもフルパスを外部アプリに渡す。外部起動後は security-scoped アクセスを10秒保持してから解放。

#### 6.4 `ZipExtractor` の純Swift化（サンドボックス対応）
*   **原因:** `/usr/bin/unzip` を `Process` で子プロセス起動していたが、**security-scoped アクセス権は子プロセスに継承されない**ため、外部ボリューム上のZIPを一切読めていなかった（サムネイル生成・表紙編集が機能せず）。
*   **対処:** 外部プロセスを廃し、`FileHandle` + `Compression` フレームワークによる**純Swiftのセントラルディレクトリ解析＋raw deflate展開**に全面書き換え。ZIP64・日本語ファイル名（UTF-8フラグ＋Shift_JISフォールバック）に対応。実ZIPで抽出・バイナリ一致を検証。

#### 6.5 サムネイル関連
*   **旧サムネイル一括移行:** インポート時に「新規追加分のみ」コピーしていたため既存2万件に反映されなかった。⚙️メニューに**「Stackroomサムネイルの移行...」**を新設し、legacyID を持つ全アイテムに対して一括コピー（進捗表示・再実行可）。
*   **ゴミ画像対策と一括修正:** 連番以外のチラシ等を表紙に拾う問題に対し、`CoverSelector` を実装。**「末尾の数字だけが異なるファイル群（連番グループ）の最大グループの最小番号」を表紙に採用**。⚙️「サムネイルの一括修正...」で、横長（横>縦）サムネイルをゴミ疑いとして連番ロジックで再抽出。
*   **破損画像フォールバック（`IIOScanner seek reached EOF`）:** デコード失敗時に候補画像を順に試す `orderedCoverCandidates` を実装。
*   **モノクロ表紙の一括修正:** ⚙️「サムネイルの一括修正...」の対象条件に「既存サムネイルがモノクロ」を追加。対象は「モノクロ」または「横長」。再生成時は連番グループの先頭画像を採用し、その画像がモノクロだった場合のみ、全画像を名前順に走査して最初の「縦長かつ非モノクロ」画像を採用する。
*   **一括修正の高速化:** 修正対象判定をメインループから切り離し、`TaskGroup` でキャッシュ済みサムネイルを並列スキャンする方式へ変更。横長判定は画像ヘッダのみで済ませ、横長でないものだけ縮小デコードしてモノクロ判定する。これにより、対象外アイテムではSwiftData解決・ZIP一覧取得・画像抽出へ進まない。
*   **ImageIO EOF警告対策:** `IIOScanner::seek reached EOF` の大量出力を抑えるため、JPEG/PNG/GIF/WebP の軽量な完全性チェックを `CoverSelector.imageDataLooksComplete` / `imageFileLooksComplete` として追加。明らかに途中切れの画像は `CGImageSource` / `NSImage` に渡さずスキップする。通常サムネイル生成、表紙編集プレビュー、モノクロ/横長判定で使用。
*   **通常サムネイル生成の表紙選定統一:** 通常のオンデマンド生成も一括修正と同じ `CoverSelector.preferredCoverData` を使用。連番グループ先頭がモノクロの場合、名前順で最初の縦長かつ非モノクロ画像へフォールバックする。例: `P001.jpg` がカラー表紙、`P007.png` 以降が最大連番グループかつモノクロの場合でも `P001.jpg` を採用。

#### 6.6 タイトル空欄の補完
*   ファイル名規則 `(ジャンル)[作者名]タイトル.zip` を解析する `FileNameParser` を実装。**先頭の `()` `[]` のみ採用（複数並びは先頭のみ）、末尾の `[]` は無視**。⚙️「ファイル名からタイトルを補完...」で空欄タイトルを一括補完。D&D新規登録でも同解析でタイトル/作者/ジャンルを自動設定。
*   **フォーマットのカスタマイズ実装:** 環境設定 > カスタマイズの「フォーマットのカスタマイズ」を実装。対応プレースホルダは `@author`（作者）, `@title`（タイトル）, `@keywordA`, `@keywordB`, `@relation`（関連）, `@genre`（ジャンル）, `@type`（種類）。書式中の `[]`, `()`, `{}`, ハイフン、ホワイトスペース等をリテラル区切りとして扱い、軽量な `NSRegularExpression` に変換してファイル名を解析する。例: `[@author(@keywordA)] @title` は `[ほげふが(太郎)] 書籍名ですよ(1).zip` を作者=`ほげふが`、キーワードA=`太郎`、タイトル=`書籍名ですよ(1)` として解釈する。同じ書式で `[ほげふが]書籍名ですよ(1).zip` のようにキーワードA部分が省略された場合は、作者=`ほげふが`、キーワードA=空、タイトル=`書籍名ですよ(1)` とする。D&D登録時は各項目へ自動入力し、`@type` は現在の種類名（カスタマイズ名または既定名）に一致した場合に `bookType` へ反映する。書式に一致しない場合は従来の `(ジャンル)[作者名]タイトル` 解析へフォールバックする。
*   **カスタマイズ画面の入力欄改善:** ダークテーマでテキストボックスが背景に溶け込んで見えづらかったため、カスタマイズ画面の入力欄をプレーンTextField＋明示的な入力背景＋細い境界線＋控えめな影に変更。フォーマット欄は記号とプレースホルダの読み取りやすさを優先して等幅フォント化した。

#### 6.7 右クリックメニュー・リストヘッダー・ソート
*   **アイテム右クリックメニュー:** スライドショー/このヘルパーで開く/削除/ゴミ箱に入れる/レート▶/種類▶/未読チェック/Finderで表示/ファイルを移動/ファイルをリネーム/表紙を編集/ファイルを再指定/並び替え▶（実機準拠）。移動・リネーム・再指定は実ファイル操作＋パス/ブックマーク更新。

*   **グリッドのソート:** 上部に「並び替え」メニューバー。

#### 6.8 ツールバー／フィルタの視認性
*   ツールバーのアイコン22pt・ラベル11pt・ボタン84×52へ拡大、SF Symbolsを塗りつぶし系（`play.rectangle.fill` 等）に統一。中央フィルタ（未読の緑丸/6色種類アイコン/レート）も拡大。★フィルタは重なって判別不能だったため **★＋数字（★1〜★5）** 表記に変更。

#### 6.9 リスト操作の安定化・キーボード対応・パフォーマンス（最難関・多段の試行錯誤）
段階的に問題が入れ替わったため経緯を残す。
1.  **初期:** 手動選択（`onTapGesture`）＋クリックは安定するが**キーボード上下移動できず**、かつ選択のたびに `filteredItems`（2万件のフィルタ＋ソート）が毎回再計算され**もっさり**。
2.  **もっさり対策:** 結果を `@State displayItems` にキャッシュし、`displayToken`（サイドバー選択・検索・各フィルタ・ソート・件数の合成文字列）が変化した時だけ `.onChange` で再計算。選択操作では再計算しない。
3.  **キーボード対応で `List(selection:)` に変更 → クリック不安定に:** ネイティブ選択の内部タップ処理が `.onTapGesture`/`.simultaneousGesture`/`.contentShape` と競合し、単クリックが効いたり効かなかったりする状態に退行。ネイティブ選択ハイライトも表示されない場面があった。
4.  **最終解:** `List(selection:)` を使わず**手動選択に戻す**（クリックが安定するのは実証済み）。キーボードは `ScrollViewReader` + `.focusable()` + `.onKeyPress(.upArrow/.downArrow/.return)` で**自前実装**（`moveSelection` が選択移動＋自動スクロール、Enterで開く）。ハイライトは `.listRowBackground` で自前描画＋選択行の文字色を白反転。
5.  **単クリックの遅延:** 単クリックとダブルクリックの `onTapGesture` 併置により、単クリックがダブル判定待ちで約0.25秒遅延していた。当初 `DragGesture(minimumDistance: 0)` で即時選択を試したが、ダブルクリックのオープン処理と競合して Enter では開くがダブルクリックでは開かない状態になった。
6.  **最終クリック処理:** 行/カードに薄い `NSViewRepresentable` (`PrimaryClickOverlay`) を重ね、左 `mouseDown` で即時選択、`event.clickCount >= 2` でオープンする方式へ変更。右クリックは `hitTest` で下の SwiftUI `contextMenu` に通す。これにより単クリックの即応性とダブルクリックの安定性を両立。

**教訓:** macOSのSwiftUI `List` では、`List(selection:)` と行の独自タップジェスチャは併用しない。大規模リストではフィルタ/ソート結果を必ずキャッシュし、選択で再計算しない。単/ダブルクリック併存時は SwiftUI の `TapGesture(count:)` だけで完結させようとすると遅延または競合が出やすいため、必要最小限の AppKit ブリッジで `mouseDown` と `clickCount` を扱う。

#### 6.10 軽量実装方針の明文化と残骸削除
*   **方針:** ShelfRow の特徴を「軽量な蔵書管理アプリ」と定義。大規模ライブラリで効く不要処理を優先して削る。
*   **削除・整理:** 未使用の `Volume` クエリ、未使用の `horizontalRadioGrouping()`、内蔵ビューア時代の未使用スライドショー表示設定（進捗/ファイル名/作品名）と環境設定UIを削除。重複して残っていた `docs/design_document.md` / `docs 3/design_document.md` も削除。
*   **表紙読み込みの軽量化:** `coverDidChange` の全件通知で全可視カバーが再ロードされないよう、個別UUID通知は対象アイテムのみ、全件通知は未読込カバーのみを再ロードする方針に変更。`CoverEditorView` のプレビューは `CGImageSourceCreateThumbnailAtIndex` で長辺900pxに縮小して表示。
*   **ZIP一覧の軽量化:** `ZipExtractor.readEntries` に、ファイルサイズ＋更新日時シグネチャ付きの `NSCache` を追加。表紙候補探索やページ一覧取得で同じZIPのセントラルディレクトリを何度も解析しない。
*   **キーボード移動の軽量化:** `selectedDisplayIndex` を保持し、上下キー移動で毎回 `firstIndex` と `scrollTo` を走らせない。`scrollTo` は端または一定距離移動時に絞る。

#### 6.11 小UI修正・一括修正のエラー抑制
*   **サイドバーフッター:** macOS の `Menu` はアイコンだけに見えてもメニューインジケータ分の幅を必要とする。`[+]` `[⚙️]` の 26pt 固定幅ではヒット領域が重なり、設定ボタンが押せない状態になったため、最小幅42pt＋適切な間隔に修正。
*   **サイドバー文字色:** ダークテーマで左ペインの見出し・項目名がシステムの二次色に引っ張られてグレー表示になっていたため、セクション見出しと行タイトルを白で明示。フォルダ/スマートシェルフのアイコン色は分類色として維持。シェルフ行は `NavigationLink` のサイドバー行スタイルが文字色を再上書きするため、画面遷移しない左ペインの性質に合わせて手動選択の `Button` 行へ変更した。
*   **D&D登録先:** 通常シェルフを表示している状態でファイル/フォルダをドラッグ&ドロップした場合、ライブラリには登録されるがそのシェルフには所属しない問題を修正。ドロップ登録時に現在選択中の静的シェルフへ `Shelf.items` を追加し、既存アイテムの再ドロップでも未所属なら追加する。スマートシェルフは条件ベースのため手動追加しない。ドロップ後は表示キャッシュを再計算し、件数が変わらない既存アイテム追加でも画面に反映する。
*   **サムネイル一括修正:** 未生成サムネイルまで `CGImageSource` に渡していたため、ライブラリが大きいほど ImageIO 系エラーが大量に出ていた。存在しないキャッシュファイルはサイズ確認対象から除外し、実ファイルがあるサムネイルだけ横長判定するよう修正。
*   **サイドバー常時表示:** ShelfRow は3ペイン前提の蔵書管理UIであり、サイドバー格納は不要。`NavigationSplitView` から `HSplitView` へ変更し、サイドバー格納機能と標準のサイドバー切替を排除。左右ペインはユーザーが調整した幅を維持し、ウィンドウサイズ変更時の増減は中央のリスト/グリッド領域で吸収する。
*   **ウィンドウ初期/最小サイズ:** `ContentView` に最小サイズを設定し、`WindowGroup` の `.defaultSize` と `.windowResizability(.contentMinSize)` を追加。デフォルトサイズは3ペインの要素が隠れず表示できる最低限のサイズを基準にする。
*   **左右ペイン幅の記憶:** `HSplitView` の内部 `NSSplitView` に `autosaveName` を設定する最小 `NSViewRepresentable` (`SplitViewAutosave`) を追加。divider 位置そのものを macOS 標準の UserDefaults 保存に任せ、次回起動時もサイドバー幅とインスペクタ幅を復元する。`GeometryReader` + `@AppStorage` 方式は復元タイミングで `HSplitView` に負けるため廃止。
*   **D&D新規登録時の種類自動判定:** 新規登録時は `@type` による明示指定を最優先し、指定が無い場合のみ画像ページ数から種類を自動判定する。21ページ以上は「厚い本」、11〜20ページは「薄い本」、1〜10ページは「本の一部」。画像フォルダを自動で「画像セット」にする従来フォールバックは廃止し、「画像セット」「テキスト」「ムービー」は自動では設定しない。ページ数は登録時に `Item.pages` にも保存する。0ページは明示ルール外として自動分類せず、必須フィールドの既定値である「厚い本」に留める。
*   **詳細設定の保守機能整理:** 実装がない扱いだった「エイリアスの復元」のボタンと説明を削除。代わりに、XMLライブラリのインポート、Stackroomサムネイルの移行、サムネイルの一括生成、ファイル名からタイトルを補完を環境設定 > 詳細設定へ移動し、各ボタンに短い説明を併記した。メイン画面の歯車メニューは環境設定とボリューム管理に絞り、詳細設定のボタンは `NotificationCenter` 経由で `ContentView` の既存メンテナンス処理を呼び出す。
*   **詳細設定の保守メニュー可読性:** 保守メニューの説明文が小さすぎたため、設定ウインドウを少し広げ、保守欄を右ラベル行から独立した全幅セクションへ変更。ボタンは大きめのコントロールサイズにし、説明文は13pt・行間付きで表示する。
*   **環境設定全体の可読性改善:** 文字が小さく全幅を使えていない箇所を整理。設定ウインドウを720×560へ広げ、共通本文サイズを13pt、セクション見出しを15ptに統一。スライドショー設定はアプリ名表示を横幅いっぱいに、ヘルパー設定は2カラムリストを広く、カスタマイズ設定は入力欄を伸縮式にして、各タブで余白を読みやすさに使うレイアウトへ変更した。
*   **詳細設定のセクション整理:** セキュリティ項目も保守欄と同じ全幅セクションとして再構成。ボリューム管理はメイン画面の歯車メニューから外し、説明付きで環境設定 > 詳細設定 > 保守へ移動した。保守ボタンは `MaintenanceAction.manageVolumes` を追加し、`ContentView` 側で既存の `VolumeRelocationView` を開く。
*   **ヘルパー設定とD&D登録の連携:** 環境設定 > ヘルパーで設定した拡張子をD&D登録の受け入れ対象に追加。拡張子は1行にカンマ区切りで複数登録でき、マッチング時はドット付き/なしを吸収する。`rar` / `zip` / `7z` はアーカイブ系としてページ数による種類判定の対象、それ以外のヘルパー登録ファイルは「ムービー」として登録する。ダブルクリック起動は拡張子ヘルパーを優先し、種類とヘルパーは独立した概念として扱う。
*   **簡易ロックの平文表示:** 簡易ロックは忘失時の回復性を優先する軽いロックとして扱う。詳細設定のパスワード欄とロック解除画面の入力欄を `SecureField` から通常の `TextField` に変更し、入力内容をマスクしない。保存は従来通り `@AppStorage("advancedPasswordValue")` への平文保存とする。
*   **ロック画面の文言修正:** ロック解除画面に旧アプリ名の「Stackroomはロックされています。」が残っていたため、「ShelfRowはロックされています。」へ修正。
*   **環境設定のモダン化:** タブ式の環境設定を廃止し、macOS Settings風のサイドバー式レイアウトへ変更。左ペインに「一般 / ビューア / ヘルパー / キーワード / カスタマイズ / セキュリティ / 保守」を並べ、右ペインに選択カテゴリの内容を表示する。一般には「メインウインドウを閉じると終了」、セキュリティには簡易ロック、保守にはボリューム管理や一括処理を配置する。
*   **メイン画面のモダン化:** `ShelfRow_modern_main_mockup.png` の方向性へさらに寄せ、グローバルな大きいツールバーを廃止。中央ペイン上部にタイトル・件数・表示切替・ソート・検索・チップ型フィルタをまとめた。未読、種類、★のフィルタは従来通り1クリックで選べる操作性を維持。左ペインはブランド行と件数バッジを持つ暗色サイドバーに、リストは暗色サーフェス上の交互背景＋角丸選択行に、右インスペクタは大きめの角丸表紙プレビューと暗色入力フィールドに調整した。
*   **リストビューの可読性改善:** モック寄せ後の行文字がやや小さかったため、タイトル列を14pt、作者・ジャンル・日付などの補助列を13ptへ拡大。種類アイコンと評価表示も少し大きくし、行高を30pt基準にして読みやすさを優先した。
*   **ヘッダーコントロール整列:** リスト/グリッド切替、並び順メニュー、検索欄の高さを36ptで統一。並び順メニューはアイコンだけの小さな表示をやめ、「並び替え」テキスト付きの116×36ptボタン面に変更。3要素の縦位置は中央揃えにし、検索欄右側にあった追加操作メニューは不要なため削除した。
*   **リスト/グリッド切替の発見性改善:** アイコンだけの小さなセグメントではユーザーが気付きにくいため、「リスト」「グリッド」のラベル付き大型セグメントへ変更。外枠42pt高、各ボタン86×34ptとし、選択中の表示モードを青い背景で明示する。
*   **サイドバーフッターの押しやすさ改善:** 左下のシェルフ追加メニューと環境設定を38×32ptへ拡大。環境設定は項目が1つだけのプルダウンだったため、直接環境設定を開くボタンへ変更した。

*   **追加ボタンの視認性改善:** 左下のシェルフ追加メニューと環境設定内の追加ボタンは、単独の `plus` では細く小さく見えやすいため、SF Symbols の `plus.circle.fill` へ変更した。
*   **スマートシェルフ追加ボタンの調整:** 左下のシェルフ追加メニューは、環境設定ボタンと同じ外形・背景に揃えつつ、`plus.circle.fill` のアイコンをやや大きめにして視認性を確保した。
*   **バックアップ設定の追加:** 環境設定 > 保守にバックアップ設定を新設。チェックボックスで有効化し、バックアップ先フォルダを選択して security-scoped bookmark として保存する。「今すぐバックアップ」でApplication Support、ShelfRowサムネイルキャッシュ、UserDefaults plistを対象フォルダの `ShelfRowBackup` へコピーする。差分判定は `manifest.json` の相対パス・サイズ・更新日時で行い、未変更ファイルはスキップ、削除済みファイルはバックアップ側からも削除する。「バックアップからリストア」も追加し、同じmanifestを正として現在側へ上書き復元する。バックアップにない対象ファイルは現在側から削除し、古いバックアップへの先祖返りを許容する。完了後はSwiftDataの再読み込みのためアプリ再起動を促す。
*   **キーワード同一視:** Stackroomの「キーワードを同一視」相当として、環境設定 > キーワードを追加。作者・ジャンル・関連・キーワードA・キーワードB・メモごとに同一視する語をカンマ/改行区切りで登録できる。検索欄にグループ内のいずれかを入力すると、同じグループの全語を同一フィールドで検索候補へ展開する。保存は `@AppStorage("keywordEquivalenceRulesJson")` のJSONとし、検索時だけ評価する軽量実装。
*   **キーワードの直接検索:** 右インスペクタの作者・ジャンル・関連・キーワードA/B・メモ欄に値がある場合、入力欄の下に検索用チップを表示するようにした。チップから「キーワードを検索」「キーワードをライブラリで検索」を実行できる。前者は現在の表示範囲で検索欄へ値を入れ、後者は左ペインを「すべての項目」に戻してライブラリ全体から検索する。検索時はキーワード同一視ルールも適用される。
*   **キーワード同一視への直接追加:** キーワードチップのメニューに「他のキーワードと同一視...」を追加。選択すると環境設定ウインドウを開き、キーワードペインへ移動し、該当する種類（作者/ジャンル/関連/キーワードA/B/メモ）と対象キーワードが入った行を先頭に追加する。既に同じ種類・同じ語の行がある場合は重複せず、その行を先頭に移動する。設定ウインドウの表示は `showSettingsWindow:` ではなく、SwiftUI の `openSettings` 環境アクションを使う。
*   **キーワード同一視の削除安定化:** 環境設定 > キーワードで行を削除した直後、`ForEach($rules)` が保持していた古い配列 Binding が削除済みインデックスを参照し、`ContiguousArrayBuffer` の範囲外アクセスで落ちる問題を修正。行は `UUID` を安定IDとして描画し、入力欄とプルダウンは都度ID検索で安全な Binding を作る方式に変更した。
*   **キーワード同一視の一括削除撤去:** 環境設定 > キーワードの「すべて削除」は誤操作時の影響が大きいため削除。ルール削除は各行の個別削除のみとする。

*   **ビルド状態:** 各段階で警告ゼロのクリーンビルドを確認済み。

## 2. ソースコード・マトリクス (Codebase Overview)

現在リポジトリに展開されている全実装ファイルの責任範囲、使用技術、引き継ぎ時の確認ポイントをMECEに整理。

### 2.1 データベース・モデル (Model Layer)
1.  **`Volume.swift`**
    *   *責務:* 外付けHDDや起動ディスクを表現する親レコード。マウントポイントの変更を吸収。
    *   *重要技術:* サンドボックスを突破するための `bookmarkData` (Security-Scoped Bookmark) の保持。
2.  **`Item.swift`**
    *   *責務:* ZIPアーカイブやコミック画像フォルダに1対1対応する、書籍データのメタデータ格納。
    *   *重要技術:* Stackroom ID (`legacyID`)をオプショナルで保持し、XMLプレイリストとのマージに活用。
3.  **`Shelf.swift`**
    *   *責務:* 標準シェルフ（本棚）およびスマートシェルフの定義。
    *   *重要技術:* スマート条件（作成日時、キーワード等）を、拡張性を担保して `smartConditionsJson` のテキストフィールドで管理。サイドバーの手動順は `sortOrder` で保持する。

### 2.2 ビジネスロジック・サービス (Logic Layer)
4.  **`LibraryImporter.swift`**
    *   *責務:* 2万件のXML PropertyListをバックグラウンドスレッドでパース・クレンジング・マージ（重複排除）し、進捗をリアルタイム送信する。
    *   *重要技術:* `@ModelActor` によるスレッドセーフなSwiftData操作、制御文字バイト除去、および旧 `thumbnail.jpg` の一括複製。
5.  **`ThumbnailCache.swift`**
    *   *責務:* 表示時の表紙画像取得。
    *   *重要技術:* `@ThumbnailCacheActor` グローバルアクター制約。メモリ `NSCache` (上限200枚) ─► 新ディスクキャッシュ ─► Stackroom資産コピー ─► `ZipExtractor` (ZIP内画像解凍) の4段階解決。カバー選定は `CoverSelector`（連番グループの最小番号）を使用し、破損画像は候補を順に試行。`setCustomCover` で表紙差し替え。アイテム個別ブックマークにも対応。
6.  **`ZipExtractor.swift`**
    *   *責務:* 外部依存ライブラリなしでZIPファイルを走査・抽出する。
    *   *重要技術:* **純Swift実装**（第6期に `/usr/bin/unzip` 子プロセス方式から全面移行）。`FileHandle` でセントラルディレクトリを解析し、`Compression` フレームワークで raw deflate を展開。ZIP64・日本語ファイル名（UTF-8フラグ＋Shift_JISフォールバック）対応。**子プロセスにsecurity-scoped権限が継承されない問題を回避するための必須変更**。セントラルディレクトリ一覧はファイルサイズ＋更新日時でキャッシュする。
7.  **`ItemFileAccess.swift`（第5〜6期）**
    *   *責務:* ファイル解決・画像列挙・パス解析・カバー選定・ファイル名解析の共通基盤。
    *   *重要技術:* `ResolvedItemFile`（security-scoped解決、アイテム個別→ボリュームの順）、`PathParser`（絶対パス→ボリューム+相対パス）、`CoverSelector`（連番ヒューリスティックによる表紙選定・横長/縦長/モノクロ判定）、`FileNameParser`（カスタムフォーマット解析＋`(ジャンル)[作者名]タイトル` フォールバック）。

### 3.2 優先して追加実装・改善すべき残余タスク

第5〜6期で主要機能はほぼ完成し、外部ビューア専業・サンドボックス対応・実データ運用の安定化まで到達。今後の改善候補:

1.  **フォーマットのカスタマイズ（@titleトークン）の実適用（唯一の明示的未実装）:**
    `renameFormat` の書式文字列は保存されるがリネーム/項目コピーに未適用。環境設定「カスタマイズ」で該当箇所を**赤表示**して未実装を明示中。
2.  **リスト操作のさらなる改善:**
    現在は手動選択＋自前キーボードナビだが、macOS標準の複数選択（Shift/Cmdクリック）は未対応。将来 `NSTableView` ブリッジ（`NSViewRepresentable`）へ移行すれば、ネイティブの複数選択・ダブルクリック・列リサイズが安定して得られる（SwiftUI `List(selection:)` は独自タップと競合するため採用しない、という第6期の結論に留意）。
3.  **表紙の見開き・先読み等はビューア側（外部アプリ）の責務**に移行済み（内蔵ビューアは撤廃）。

### 3.3 落とし穴・再発防止メモ（第6期の教訓）
*   **サンドボックス:** 外部ボリューム/旧アプリフォルダへのアクセスは必ず Security-Scoped Bookmark 経由。`ShelfRow.entitlements` の `bookmarks.app-scope` が無いとブックマーク生成が例外になる。子プロセス（`Process`）にアクセス権は継承されないため、ZIP展開等は必ずアプリ内（純Swift）で行う。
*   **SwiftUI List:** `List(selection:)` と行の `.onTapGesture`/`.simultaneousGesture` は併用しない（クリックが不安定化）。選択・キーボードナビは自前実装。
*   **複数 `.alert`:** 同一ビューに複数の `.alert` を付けると片方しか機能しない。別ビュー（`.background` 等）へ分離する。
*   **大規模リスト:** フィルタ/ソート結果は `@State` にキャッシュし、選択操作で再計算しない（`displayToken` 方式）。
*   **単/ダブルクリック併存:** SwiftUI の `TapGesture(count:)` だけでは単クリック遅延やダブルクリック競合が起きやすい。現在は `PrimaryClickOverlay`（最小限の `NSViewRepresentable`）で左 `mouseDown` 即時選択、`clickCount >= 2` でオープン、右クリックは SwiftUI `contextMenu` へ通す。
*   **ドキュメント:** 実装方針や挙動が変わったら、必ず `documents/update_history.md` と `documents/design_document.md` を同時更新する。
