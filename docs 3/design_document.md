# ShelfRow (Stackroom Remake) 設計仕様書 (Design & Architecture Document)

本ドキュメントは、レガシーmacOSアプリケーション「Stackroom」のコンセプトと資産（ライブラリデータ、表紙サムネイル）を現代のmacOS（SwiftUI / SwiftData）環境に継承・近代化し、セキュアかつ高速に動作させるための設計仕様である。

他開発者（人間およびAI）が、本システムの設計背景、意図、モデリング、およびデータ構造をMECE（相互に排他的で、全体として漏れがない）に理解し、実装・保守できることを目的とする。

---

## 1. 背景と課題 (Background & Context)

### 1.1 背景
「Stackroom」は、2004年頃にリリースされた、自炊（スキャン）したコミック、同人誌、画像フォルダ、ZIPアーカイブをiTunesライクに整理・管理・閲覧できるmacOSアプリケーションである。
長年にわたりメンテナンスが停止しているが、その操作性の高さと優れた蔵書管理機能から、膨大な蔵書資産を抱えるユーザーにとって代替困難な存在となっている。

### 1.2 解決すべき課題
1. **インフラの近代化:** 
   旧アプリはローカルメモリ上ですべてを処理し巨大なXMLファイル（実際はPLIST形式）で永続化していた。書籍数が2万件近くなると起動時間や保存時のI/O負荷が限界に達するため、堅牢なリレーショナル・データベース（RDB）による遅延ロードが不可欠。
2. **サンドボックスとセキュリティ制約への適応:** 
   現代のmacOSのセキュリティモデル（Sandbox）下では、アプリ外部のストレージ（外付けHDD、NAS等）にある書籍ファイルへのアクセス権限を安全に永続保持（Security-Scoped Bookmark）する必要がある。
3. **パス一括付け替え問題:** 
   外付けドライブの買い替えやマウントポイントの変更によって書籍データの絶対パスが変わった際、数万件外部のフォルダ情報を個別に書き換えることなく、一括でアクセス権とパスをマッピングできる構造が必要。
4. **レガシー資産（サムネイル画像）の完全インポートと自立化:** 
   旧アプリが生成した約2万件の表紙サムネイル画像（`thumbnail.jpg`）を、一度のXMLインポート処理で完全に新アプリ側のローカルストレージへコピー移行し、インポート完了後に旧アプリフォルダを安全に完全削除できる仕組みが必要。

## 2. システム要件・仕様 (Requirements & Specifications)

### 2.1 機能要件 (Functional Requirements)
*   **レガシーXMLインポート:** 旧アプリの `Stackroom Library.xml` を非同期でパースし、書籍・フォルダ階層・スマートフォルダ定義を完全移行。
*   **制御文字の自動クレンジング:** 旧アプリのバグや古いPLIST保存APIが書き出した、XML 1.0仕様違反の不正な制御コード（`\x01`〜`\x08`等）を事前検知・自動除去。
*   **一括サムネイル移民（マイグレーション）:** インポート時に、旧アセットフォルダ（`Stackroom Library/[ID]/thumbnail.jpg`）から新アプリのプライベートキャッシュ領域へサムネイル画像を物理的に丸ごとコピー。
*   **ボリュームベース相対パス管理:** 書籍ファイルを「親ボリューム（絶対マウントパス＋権限）」と「相対パス」に分離して保持し、ボリューム移行時は「親ボリューム」のみを再選択して再解決する。
*   **3ペイン macOS ネイティブ UI:** ミュージックアプリ（旧iTunes）に倣ったサイドバー、メインコンテンツ（グリッド/リスト）、編集インスペクタを搭載。
*   **外部ビューア連携 & Finder表示:** お気に入りの外部コミックビューア（EdgeView等）でのファイル起動、およびFinder上での選択ファイル表示。

### 2.2 非機能要件 (Non-Functional Requirements)
*   **応答性 (Responsive UI):** メインスレッド（UI描画）を絶対にブロックしない。2万件のインポート、サムネイル生成、パスの書き換え、ビューアの起動、すべてを Swift Concurrency (`Task` / `actor`) で非同期化。
*   **メモリ効率 (Memory Efficiency):** 2万件の画像を一度にRAMへロードしない。`NSCache` による画面外画像の自動パージと、`CGImageSource` の縮小サムネイル切り出しAPIを用いたメモリ負荷軽減。
*   **機密性 (Security):** 外部ボリュームへのアクセス権をmacOSの `Security-Scoped Bookmark` を通じて安全にディスク保存する。

## 3. アーキテクチャ設計 (System Architecture)

### 3.1 データベース設計 (Database Schema via SwiftData)

データベースエンジンには、Core Data（SQLiteバックエンド）の最新のラッパーである **SwiftData** を採用。

```
                       ┌──────────────┐
                       │    Volume    │
                       └──────┬───────┘
                              │ 1
                              │
                              │ 0..*
                       ┌──────▼───────┐
                       │     Item     │
                       └──────┬───────┘
                              │ 0..*
                              │
                              │ 0..*
                       ┌──────▼───────┐
                       │    Shelf     │
                       └──────────────┘
```

#### ① Volume (マウント・外部メディアエンティティ)
物理的なドライブ、パーティション、またはネットワーク共有フォルダを抽象化したエンティティ。
*   `id`: `UUID` [Primary Key] - 内部一意識別子
*   `name`: `String` - ユーザー向けのドライブ・フォルダ表示名 (例: "Manga HDD")
*   `lastKnownPath`: `String` - 最後にマウントが確認された絶対パス (例: `/Volumes/MangaDrive`)
*   `bookmarkData`: `Data?` - macOSのセキュア永続アクセス用のセキュリティ・スコープ・ブックマーク

#### ② Item (書籍エンティティ)
管理対象となる個々のZIPファイルまたはフォルダ。
*   `id`: `UUID` [Primary Key] - 内部一意識別子
*   `legacyID`: `Int?` [Unique Index] - 旧Stackroomの「ID」（プレイリストのバインドに必須）
*   `volume`: `Volume?` [Relation (Optional)] - この本が属するマウントボリューム
*   `relativePath`: `String` - ボリュームルートからの相対パス (例: `Completed/Title.zip`)
*   `title`: `String` - 書籍タイトル
*   `author`: `String` - 作者・サークル名
*   `rating`: `Int` - 5段階評価のレート (0〜5)
*   `isUnread`: `Bool` - 未読フラグ（旧XMLの `Unseen` からマッピング）
*   `pages`: `Int` - ページ数
*   `bookType`: `Int` - 書籍タイプ（単行本、同人誌、雑誌等のオリジナル数値）
*   `fileType`: `Int` - ファイルの種類（ZIP, フォルダ等のオリジナル数値）
*   `genre`: `String` - ジャンル名（旧メタデータのカスタムマッピング先）
*   `relation`: `String` - 関連作品
*   `keywordA`: `String` - 検索タグA
*   `keywordB`: `String` - 検索タグB
*   `memo`: `String` - メモ（旧XMLの `Neta` からマッピング）
*   `addedDate`: `Date` - ライブラリ登録日時
*   `lastReadDate`: `Date?` - 最終読込/プレイ日時
*   `shelves`: `[Shelf]?` [Relation (Many-to-Many, Inverse)] - 紐づくフォルダ（シェルフ）のコレクション

#### ③ Shelf (フォルダ・プレイリストエンティティ)
ユーザーが自由に編成、または条件を指定して生成する仮想本棚。
*   `id`: `UUID` [Primary Key] - 内部一意識別子
*   `title`: `String` - 本棚名
*   `icon`: `Int` - アイコンタイプ値
*   `type`: `Int` - プレイリストの種類 (0: 静的シェルフ, 1: 条件付きスマートシェルフ)
*   `sortKey`: `String` - 本棚内での表示ソートキー
*   `sortAscending`: `Bool` - 昇順/降順
*   `smartConditionsJson`: `String?` - スマートシェルフの検索・日付条件フィルタ辞書のJSONシリアライズ文字列
*   `items`: `[Item]?` [Relation (Many-to-Many)] - 静的シェルフに所属する Item の実体リスト

## 4. パス変換とマウント解決ロジック (Path Resolution Engine)

絶対パスからボリューム境界を自動検出し、サンドボックス対応の相対パス解決をおこなう。

```
[絶対パス]  "/Volumes/MangaStorage/Files/Comic.zip"
                       │
                       ▼ (解析・コンバート)
   1. Volume検出 ──► ルートパス: "/Volumes/MangaStorage" (Volumeレコード生成)
   2. 相対パス抽出 ─► 相対パス:   "Files/Comic.zip" (Itemレコード生成)
                       │
                       ▼ (再構築・アクセス時)
   1. Volume.bookmarkData を解決 ──► 現在の絶対マウントパスを取得
   2. 相対パスと結合 ─────────────► フルアクセスURLとしてファイル操作開始
```

1.  **絶対パスの分解:** 
    インポート時、パスの接頭辞が `/Volumes/VolumeName/...` であれば `/Volumes/VolumeName` をマウントポイントとして `Volume` を初期化（未作成時）。残りの `/Files/...` を `Item.relativePath` に格納。そうでない場合はシステム起動ドライブ `/` を `Volume` として処理。
2.  **実行時のセキュリティScoped解決:**
    ファイルへのアクセス時は、必ず `Volume.bookmarkData` の解決を試みる（`URL(resolvingBookmarkData:options:...)`）。取得した安全なURLに対して `startAccessingSecurityScopedResource()` を呼び出した上で、相対パスを結合してアクセスする。

## 5. サムネイルキャッシュ設計 (Thumbnail Cache Strategy)

2万件の書籍に対して、画面のスクロール追従性と省メモリを両立させるためのハイブリッドなアーキテクチャ。

```
                      getCoverImage(for: Item)
                                │
          ┌─────────────────────┴─────────────────────┐
          ▼ 1. メモリキャッシュ (RAM)                 ▼ 2. ディスクキャッシュ
      [NSCache]                                 [~/Library/Caches/.../Thumbnails/]
  (デコード済・極超高速)                                 (ファイルシステム・高速)
   ・ヒット ──► 描画                                     ・ヒット ──► NSCacheに展開 ──► 描画
   ・ミス ────┐                                         ・ミス ────┐
              │                                                    │
              └─────────────────────┬──────────────────────────────┘
                                    │
                                    ▼ 3. 物理抽出 or 旧アセット移行
                        ┌───────────┴───────────┐
                        ▼ (JIT抽出 / インポート)   ▼ (旧Stackroomサムネイル)
                     [ZIPFoundation]      [Stackroom Library/ID/thumbnail.jpg]
                     (ZIP内最初画像)
                        │                       │
                        └───────────┬───────────┘
                                    │
                                    ▼ 4. CGImageSource で 400px に縮小
                                    │
                                    ▼ 5. キャッシュディスクにJPEG保存 ＆ NSCache格納 ＆ 描画
```

1.  **物理コピー（インポートフェーズ）:**
    XMLインポートのバックグラウンドタスク実行中に、`item.legacyID` を手がかりにして `~/Library/Application Support/Stackroom/Stackroom Library/[legacyID]/thumbnail.jpg` から、新アプリの `Caches/jp.aromatics.ShelfRow/Thumbnails/[item.id].jpg` へファイルを直接物理コピーする。
2.  **オンデマンド抽出（JITフェーズ）:**
    旧サムネイルが存在しない新規登録の書籍などは、ビューアへの表示要求時にバックグラウンドスレッドでZIP内の最初のエントリファイルまたは画像フォルダを探索・走査し、カバーデータを取得する。
3.  **高速ダウンスケーリング:**
    `CGImageSourceCreateThumbnailAtIndex` APIを使用し、画像をフルピクセルで展開することなく、メモリ制限（長辺最大400px）内に収まる縮尺のサムネイルをGPUフレンドリーにデコード。これにより数MBの画像であってもわずか数KBのメモリでロードが完結する。
4.  **NSCache 制限:**
    RAM内のメモリキャッシュは最大200枚に制限。制限を超えた画像はOSがGCを走らせる前に自主的に消去・パージされ、アプリの異常終了（OOMエラー）を100%防止する。

## 6. モジュール・クラス設計 (Detailed Class Design)

### 6.1 `LibraryImporter` (バックグラウンドインポーター・ModelActor)
インメモリでXMLを安全に解析し、マルチスレッドをブロックせずにDB登録を実行する独立アクター。
*   **構造:** `actor LibraryImporter: ModelActor`
*   **プロパティ:**
    *   `modelExecutor: ModelExecutor` (SwiftDataのモデル保存実行機構)
    *   `modelContext: ModelContext` (アクターに完全に分離されたスレッドセーフなDB書き込み領域)
*   **公開API:**
    *   `importLibrary(from url: URL) async throws -> (booksCount: Int, playlistsCount: Int)`
*   **主要アルゴリズム (XMLクレンジング):**
    XMLパーサーは規格（XML 1.0）違反の制御文字（SOH: `\x01` 等）を検出するとエラーで即時停止する。アクター内部で事前に生データ `Data` を走査し、`0x00-0x08`, `0x0B-0x0C`, `0x0E-0x1F` (タブ、改行、キャリッジリターン除く) をバイパスするバイトバッファ再構築を高速実行（約10〜20ms）してからPLIST展開をおこなう。

### 6.2 `ThumbnailCache` (表紙・サムネイル解決管理アクター)
スレッドセーフなキャッシュ読み込み、ディスクキャッシュ保存、ZIP解凍連携をすべて集約した管理クラス。
*   **構造:** `actor ThumbnailCache` (グローバルアクター `@ThumbnailCacheActor` 制限)
*   **公開API:**
    *   `getCoverImage(for item: Item) -> NSImage?`
    *   `clearCache()`
*   **依存関係:**
    *   `ZipExtractor` (ZIPファイル走査・抽出処理ユーティリティ)


#### 7.2 各画面とUI連携要素
1.  **Sidebar (左ペイン):**
    *   シェルフ（標準・スマート）のツリー表示、選択したシェルフによるメインビューのフィルタ条件のリアルタイム切り替え。
    *   フッター部アクションからXMLインポーターシートとボリュームマネージャーシートを呼び出し。
2.  **Main Content (中央ペイン):**
    *   **フィルタヘッダー:** 任意の文字列検索＋未読フィルタ切り替え＋評価レートの星別フィルタを網羅。
    *   **グリッド表示:** サムネイルローダー `CoverImageView` を配した適応型グリッド（`LazyVGrid`）。
    *   **リスト表示:** macOSのネイティブ感を引き出す、表紙・タイトル・作者・ページ数・レート・未読ドット（青）を並べた行リスト表示。
    *   **ビューア起動:** ダブルクリック時、`NSWorkspace.shared.open` をコールし、システムデフォルトのコミックビューア（または独自ビューア）へ高速にファイルパスを安全に委譲。
3.  **Inspector (右ペイン):**
    *   選択されたItemにバインドされたリアルタイムフォーム。テキスト編集、レート評価星のクリック、未読トグル切り替え時に、DBにトランザクション不要で即時自動保存が走るリアクティブなフォーム構造。

## 8. MECEな例外・エラー処理マトリクス (Exception Handling Matrix)

起こり得るエラー状態と、その発生レイヤー、回避設計を重複なく整理（MECE）。

| カテゴリ | 具体的な異常ケース | 発生レイヤー | アプリケーション側の回避・復旧設計（堅牢化設計） |
| :--- | :--- | :--- | :--- |
| **XMLインポート** | XML 1.0仕様違反の制御文字（SOH等のバイナリゴミ）の混入 | `LibraryImporter` | 事前に raw Data バッファを高速スキャンし、禁止バイト配列のみを除外してクリーンアップしてからパースを実行。 |
| **XMLインポート** | プレイリストにXML内に実在しない書籍IDが含まれている | `LibraryImporter` | インポート時に書籍キャッシュ辞書からマッチングし、存在しないIDは無視して静的シェルフの紐付けをおこなう（クラッシュ回避）。 |
| **ファイル解決** | 外付けHDDが取り外されている / パス名が変更されている | `ThumbnailCache` / `ContentView` | 物理的なファイルチェックに加え、セキュリティ・スコープ・ブックマーク解決が失敗した場合、アイテムは「未接続」状態とし赤シグナルを表示、再割り当て設定をユーザーへ即座に案内。 |
| **ファイル解決** | 書籍ファイルそのものがすでに削除・紛失している | `ContentView` / Viewer | ファイルオープン前に `FileManager.default.fileExists` で厳密確認し、欠落時はダイアログでユーザーに警告を出し、Finder遷移や不要なアプリフリーズを抑止。 |
| **キャッシュ解決** | メモリが逼迫し画像ロードによりOOM（Out Of Memory）が発生 | `ThumbnailCache` | `NSCache` のカウントリミットを 200 に設定し、超過したデコード画像は自動でメモリパージ（RAM安全域確保）。 |
| **キャッシュ解決** | ZIPファイルの最初の画像を抽出するが、破損している | `ThumbnailCache` | `CGImageSource` のサムネイル生成失敗を検知した時点で、プレースホルダー本棚画像へセーフティに縮小・フォールバック。 |

## 9. 開発・検証方針 (Verification Plan)

本設計ドキュメントに基づき、段階的なビルド・動作テストを以下のパスで進行する。
1.  **SwiftData構造検証:** `Volume`, `Item`, `Shelf` スキーマが完全に構築・定義され、Xcodeビルドが通ることをテスト。
2.  **インポーター検証:** ダミーの壊れたXML、および2万件規模の `Stackroom Library.xml` を読み込ませて、制御コードが正常パージされ、データと既存 `thumbnail.jpg` が正しくコピー・登録されるかを確認。
3.  **UI表示・スクロールパフォーマンス検証:** グリッド/リストスクロールが60fpsに近い滑らかさで動き、メモリ（RAM）リークが起きないことをInstruments（Xcodeツール）またはアクティビティモニタで検証。
4.  **ボリューム変更検証:** パスを変更した後に「フォルダーを再割り当て」を実行し、元のアイテムに対するブックマーク解決とアクセス権が全自動で復活することを確認。
